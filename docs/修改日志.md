# 修改日志 — Web 对话"几轮后不再说话"故障修复

**日期**：2026-10-26
**现象**：Web 界面（:55556，经 tailscale https://…:8443 访问）对话几轮后系统永久沉默；ASR 与轮次检测始终正常，LLM/语音无响应，且不能自愈。

---

## 1. 根因（诊断结论，只读排查得出）

三层问题叠加，最终死锁在 FireRedTTS 服务：

1. **死锁本体**：`full_duplex/frc_services/tts/server.py` 的流式合成把全局
   `SYNTH_LOCK` 横跨整个 `while True` 循环（含 `yield`）。客户端中途弃读但不关
   socket 时，生成器停在锁内的 `yield` 上永久休眠 → 所有后续 TTS 请求在锁上排队；
   每个排队请求占一个 anyio 线程池线程（默认 40 个），客户端超时后线程仍卡在锁上
   不归还 → 线程池耗尽，连 `/health` 都挂起，GPU 0%、无 I/O——纯锁死。
   （实测现场：旧进程对 SIGINT 无响应，最终 `kill -9` 才死。）
2. **触发器**：web app 每收到新话轮无条件打断上一轮（`app.py` 的
   `interrupt()`），打断路径 `break` 丢弃正在迭代的 TTS 生成器；requests 的
   Response 未在 finally 中关闭，socket 残留（现场残留 4 条 web→8081、25 条
   6007→8081 僵尸 ESTABLISHED 连接）。**必须等一次抢话恰好遗弃一条合成中的流才
   触发，所以"前几轮正常"。**
3. **放大器**：融合服务 `qwen35_fused_server.py` 的 `_stream_tagged` 在 `/chat`
   纯文本端点上**照样为每个文本段做内部 TTS 再丢弃**，且在吐后续文本之前同步等
   它（180s 超时）。TTS 一旦锁死，每段文本被拖 180 秒 → 客户端 60s 读超时 →
   永远 "Sorry"（这句也 TTS 不出来）。另外 `_stream_tagged` 没有 finally 置
   cancel，被打断的请求在服务端跑满 512 token 持 GEN_LOCK（僵尸排队）。

## 2. 修改清单

### 2.1 `full_duplex/frc_services/tts/server.py`（死锁根治）
- `_speech_stream()`：`with SYNTH_LOCK:` 从"横跨整个流式循环"（原 287 行）
  改为**仅包住单次 `model.synthesize_online()` 调用**（现 300 行），`yield`
  移到锁外。
- 效果：GPU 访问仍全局串行，但被弃置的流不再持有任何锁；并发流之间按块交错
  （各自客户端收到的块顺序不变）。
- ⚠️ 该文件同时被 **full_duplex 的 FRC agent**（frc_worker 等，端口 8081）
  使用，本次修复对两者同时生效。

### 2.2 `soulx/services/qwen35_fused_server.py`（去掉无效 TTS + 僵尸生成）
- `_stream_tagged()`（170 行）新增 `tts=True` 参数：`/chat` 以 `tts=False`
  调用（267 行），**完全跳过内部 TTS**——web app 本来就自己直连 TTS 合成，
  这里的合成结果本来就被丢弃，纯耗延迟。
- 主消费循环包进 `try/finally`（242–247 行）：正常结束、异常、GeneratorExit
  （客户端断开/响应被取消）一律 `cancel.set()`，generate 线程立刻停止并释放
  GEN_LOCK，不再跑满 512 token。

### 2.3 `soulx/repo/dialogue_system/clients/llm_client.py`（连接泄漏）
- `QwenLLM_stream.generate_with_history`（102 行 finally）与
  `QwenLLM_IndexTTS_stream.generate_with_history`（174 行 finally）：
  response 的关闭从"仅 stop_event 分支"改为 **finally 全路径关闭**
  （正常结束 / stop / 60s 超时异常）。超时异常路径原先从不关连接——每次超时
  泄漏一个连接且服务端看不到断开、继续僵尸生成（现场 17 条泄漏连接的来源）。

### 2.4 `soulx/repo/dialogue_system/clients/tts_client.py`（死锁触发器）
- `FireRedTTS.synthesize`（127 行 finally）：流式迭代包进
  `try/finally response.close()`。生成器被中途弃置（抢话打断 break）时 socket
  必定关闭，TTS 服务端不再向死读者持续写。

**未改动**（有意保留）：GEN_LOCK 的全局串行（单卡单实例的正确设计，取消机制
已让锁及时释放）；`llm_client` 60s 读超时；turn server 与 web app 的打断逻辑
（属轮次检测设计）；TTS 服务 `whole` 流式模式中原有的
`chunk=req.input` 每轮重复理论问题（非本次故障路径，FRC 侧实际走非流式，未触碰）。

# 修改日志 — 第二次"几轮后无响应 / 不再转写"故障:浏览器 WS 掉线后前端无重连

**日期**:2026-10-26(同日,端口迁移后)
**现象**:几轮交互后系统不再说话,且前端 User Transcription 对新输入的语音也不再转写(页面不刷新就一直沉默)。

## 1. 诊断过程

### 1.1 排查工具建设(本轮新增,保留备用)

- `app.py`:SIGUSR1 注册 faulthandler(全线程栈);SIGUSR2 自研 asyncio 任务转储
  (walk `task.get_coro() → cr_frame/cr_await` 链,faulthandler 看不到挂起的协程)。
- `repo/server.py`(turn server):SIGUSR1;`feed_audio` >0.5s 打印。
- `clients/vad_client.py`:`process()` 异常不再静默(`bare except` → 记录类型与耗时)。
- 新增 `scripts/e2e_web_test.py`(浏览器会话模拟,6 轮真实音频流 + 看门狗)、
  `scripts/turn_probe.py`(绕过 web 直连 turn server)、`scripts/wedge_monitor.py`。
- 本机 yama `ptrace_scope=1`,py-spy/gdb/strace 均不可用——以上是替代方案。

### 1.2 自坑:e2e 客户端音频编码 bug(重要教训)

`e2e_web_test.py` 原先把 float32 [-1,1] 音频直接 `astype("<i2")`——全部截断为
**int16 零**,即第 1–12 轮 e2e"复现"全程给服务器发纯静音,所谓"卡死"其实是
系统对静音的正确应答。修复:`(np.clip(x,-1,1)*32767).astype("<i2")`。
**教训:复现脚本本身必须先证明自己发出的数据是对的(客户端打印 head hex +
服务器端打印 rms 双向核对)。**

### 1.3 修复后真实音频 e2e 全通过 → 服务端管线无罪

修复编码后 6 轮真实音频 e2e(第 13/14 轮)全部通过:每轮 33.6s 语音,转写
744/752 条、LLM 响应 16/15 条、音频正常下发、无 STALL。

### 1.4 用户会话日志取证(web.log)

- **18:06:22–18:08:22 会话**:15 轮正常;最后两轮(18:08:17/18:08:18)ASR 有
  结果但 5s 内无 LLM chunk——融合服务 `GEN_LOCK` 全局串行下快速抢话排队 +
  GPU 争用导致的**暂态**延迟(可自愈);18:08:22 WS 被客户端侧关闭。
- **18:13:52 会话**(用户重开页面):`config_audio` 已到达(说明点了开始、
  getUserMedia 成功),但之后**一个音频字节都没到服务器**;整 **40.0 秒**后
  被 uvicorn websockets 的 ping_interval(20s)+ping_timeout(20s) 关闭——
  典型**半死 TCP**:浏览器端 `send()` 不报错、`readyState` 保持 OPEN,
  所有麦克风音频进了网络黑洞。40.0s 的整数间隔正是 ping 超时的指纹。

### 1.5 根因

前端 `script.js` 的 `socket.onclose` 只打一条 console.log,**没有任何重连
逻辑**;发送侧 `if (socket.readyState === OPEN)` 对半死连接也永远"通过"。
于是:WS 一旦掉线(tailscale 网络抖动、电脑休眠/唤醒、切换网络等),
**转写与应答走同一条连接,全部停止**,页面看似正常却永久沉默——与用户
"没反应了、新语音也不转写"完全吻合。

## 2. 修改清单

### 2.1 `repo/dialogue_system/frontend/script.js`(根治:自动重连 + 心跳)
- `connectSocket()`:socket 创建收拢为函数,断线后**指数退避重连**
  (0.5s 起步,封顶 5s,`onclose` 必触发)。
- **应用层心跳**:每 8s 发 `{"event":"ping"}`,任何服务器消息都算活跃;
  **25s 无任何下行则强制 `close()` 触发重连**——这是检测半死 TCP 的唯一
  手段(浏览器感知不到,协议层 pong 由浏览器自动应答)。
- 重连成功后:若在录音则**重发 `config_audio`**、`abort` 旧 TTS 播放。
- `loadingConfirmedOnce`:重连后服务端会重发 `vad_loading`,不再要求用户
  再点一次 "Start Experience"(否则重连体验恰好复刻"页面死掉"的表象)。
- 新增 `pong` 事件分支。

### 2.2 `repo/dialogue_system/frontend/index.html` / `style.css`

- 删除首块 head-hex 调试日志(vad_client 侧的周期性 `call#` 打印一并删除;
  保留异常路径与慢调用日志)。

### 2.4 `repo/dialogue_system/clients/vad_client.py`
- `connect()`:`create_connection(..., timeout=5.0)`——原先无超时,turn
  server 卡住会**永久阻塞 web 事件循环**。
- `reset()` 容错:close 包 try、reconnect 失败置 `ws=None` 并打印(配合
  2.3,实例必定回池)。
- `process()` 顶部懒连接(`ws is None` 才 connect)——池实例初始化不再
  预连 10 条闲置 socket(闲置 socket 会因 uvicorn ping 超时逐个死掉)。

### 2.5 脚本

# 修改日志 — 公司内网访问:麦克风/Audio Engine 报错(非安全上下文)

**日期**:2026-10-26(同日,第三次)
**现象**:内网 `http://172.31.48.7:8090/` 页面可打开,但报
"Audio Engine initialization failed! Only supported in localhost or https",
麦克风不可用;tailscale(https)访问一切正常。

**原因**:浏览器安全策略——`getUserMedia`(麦克风)与 `SharedArrayBuffer`
(前端 TTS 环形缓冲)是 **Secure Context 专属 API**,仅在 `https://` 或
`http://localhost` 下暴露。明文 http + 非 localhost 的源属于非安全上下文:
`SharedArrayBuffer` 为 `undefined` → `initTTSAudioEngine()` 抛 TypeError(弹窗),
`navigator.mediaDevices` 为 `undefined` → 录音不可用。app.py 的 COOP/COEP
响应头只负责 cross-origin isolation,无法改变 Secure Context 判定。
**服务端任何改动都消除不了该报错,必须换 https(或 localhost)访问。**

另发现:内网直连 `https://172.31.48.7:8443` 会命中 root caddy 的默认站点,
打开的是**旧的 frc_eot_demo**(:9800),不是本服务——不要用该地址。

**修改**(方案①,用户确认后实施):
- 新增 `services/https_proxy.py`:asyncio TLS 反代,`0.0.0.0:8444`(TLS,
  自签证书)→ `127.0.0.1:8090`。纯字节管道,WebSocket 升级透传。
- 新增 `services/certs/intranet-{cert,key}.pem`:自签证书(OSSL 10 年,
  SAN 覆盖本机全部 IP:172.31.48.7、33.192.2.130/162、33.192.10.130/162、
  100.121.43.98、127.0.0.1、localhost)。浏览器首次访问会有一次
  "连接不是私密连接"警告,点"高级→继续前往"即可。
- tmux `soulx:intranet` 窗口常驻,日志 `logs/https_proxy.log`。

**验证**:
- `https://172.31.48.7:8444/` 返回本应用页面(title "Full-Duplex Speech
  Dialogue"),`/script.js` 200;
- wss 全链路(经 TLS 反代):真实音频流式输入 → ASR 转写 OK、vad_status OK、
  心跳 pong OK。

**备选方案**(未实施):
- 方案②:root caddy(`/etc/caddy/Caddyfile`,需 sudo)加
  `https://172.31.48.7:8443 { tls internal; reverse_proxy 127.0.0.1:8090 }`,
  可用标准端口并顺带修掉"IP 访问 8443 打开旧 demo"的混乱;
- 方案③:客户端 Chrome flag
  `chrome://flags/#unsafely-treat-insecure-origin-as-secure` 填
  `http://172.31.48.7:8090`(每台机器单独设置,重启浏览器生效)。

# 修改日志 — 主说话人门控（PVAD）+ 浏览器回声消除

**日期**：2026-10-29
**需求**：接入 FireRedChat 的 AEC/降噪/语音增强模块与 PVAD。硬性约束：
**PVAD 不得影响、不得阻塞 SoulX 轮次控制器的流式处理**——只作为
"是否为主说话人"的判别增强模块。

## 1. 方案要点

- **AEC/降噪**：FireRedChat 本身没有服务端 AEC 模型，其官方 demo 即用
  浏览器 WebRTC 处理链。故 `getUserMedia` 约束改为
  `echoCancellation + noiseSuppression + autoGainControl` 全开（用户确认）。
- **PVAD**：fireredchat-pvad 插件（ONNX 个性化 VAD 3.8MB + speechbrain
  ECAPA-TDNN 86MB）封装为独立 sidecar `services/pvad_server.py`
  （:8086，CPU），运行于 `full_duplex/venv-frc`（唯一带
  speechbrain/onnxruntime 栈的环境；跨 venv 复用模式同 eot_bench 的
  ultraVAD，不动 full_duplex 任何代码，只借用其 venv 读
  fireredchat_ref 插件）。必须 `HF_HUB_OFFLINE=1`：插件仓库顶层
  `spkrec-ecapa-voxceleb/` 是空占位目录，真权重在 `resources/` 下，
  在线模式会让 speechbrain 去 HF 拉取然后报错。
- **非阻塞架构（核心约束的落实）**：
  - 音频接收循环只做旁路三件事（均在 `session.lock` 外、`vad.process`
    之前）：`pvad.feed(chunk)`（纯队列 put）、`mic_ring` 追加 160ms chunk
    （独立 `ring_lock`，30s 环形）、节流 1.5s 的 `pvad_status` 遥测。
    **`vad.process` 的轮次控制路径一行未动。**
  - 唯一阻塞调用 `score()`（ECAPA 前向 ~120-170ms）只发生在 worker
    线程：话轮门控在 `pipeline_worker` 开头，抢话门控在独立 daemon
    线程（`pvad_checking` 标志去重并发请求）。
  - **fail-open**：未注册 / ring 语音 <1s / sidecar 不可达 → 一律放行。
  - **自动注册**：首个过门控的话轮从 ring 语音注册主说话人（<3s 语音
    推迟、下轮重试）；前端 Re-enroll 按钮可手动重注册。
  - 三态模式 off / shadow / enforce（默认 enforce）+ 相似度阈值
    （0.3-0.9，默认 0.5）可在 Settings 实时调，被拒事件以
    `pvad_reject {kind, cos, threshold, shadow}` 推给前端闪现提示。

## 2. 关键转折：门控信号从 pvad 概率换成 ECAPA 余弦（实测数据）

最初设计用 pvad 概率（speech-conditioned 窗口均值）做门控，逐代探针
否掉了它——**pvad 概率在硬负例上无法区分说话人**：

| 探针 | 结果 |
|---|---|
| 窗口均值（语音段） | 说话人 B 0.54 vs 主说话人 A 0.60 —— 无分离 |
| 完全无关的英文播客 | **0.77，高于注册者本人 0.58** |
| GRU 状态隔离（fresh / A-warm / sil-warm） | 全部 ~0.47-0.54，状态不是原因 |
| 同插件 ECAPA 余弦 | **同人 0.59-0.80，异人 0.06-0.44** —— 干净分离 |

结论：pvad 概率只配当"当前有无语音活动"的 UI 遥测；身份判别用同一
插件里的 ECAPA 说话人嵌入余弦，阈值 0.50（`/score` 端点即为此加）。
这条弯路的价值是把"为什么不是 pvad 概率"用数字钉死了。

## 3. 打分窗口的坑（两轮误拒排查）

- **max-RMS 窗口失败**：抢话/话轮判定常落在静音段，ring 尾部最优 5s
  窗口 = 4.5s 零 + 一小截语音——RMS 过阈但 ECAPA 出垃圾嵌入（实测同人
  余弦跌到 0.16，两轮 e2e 误拒）。
- **修复 `_pvad_ring_speech`**：取最近 8s、切 160ms 块、只拼
  RMS ≥0.015 的语音块（上限 ~5s / 31 块）；拼接不足 1s → fail-open。
  修复后 e2e 6 轮 0 误拒。

# 修改日志 — VoxCPM2 跨段音色漂移修复 + 自训练 LoRA 接入

**日期**：2026-10-29（同日，PVAD 之后）
**现象**：web 对话中 VoxCPM2 的跨段一致性差，音色与情绪漂移严重；用户怀疑
未开启克隆音色，并提供了自训练 LoRA
（`/vepfs-cnbjc4e12c6d7e1f/krisl/step_0000500`，包原生格式，r=32/alpha=32，
enable_lm+enable_dit）。要求：保持流式输出、不用文本描述音色、默认音色。

## 1. 漂移根因（代码级定位，非猜测）

旧服务走 **zero-shot 模式**：每次 `generate_streaming` 的 CFM 采样从新高斯
噪声开始（`voxcpm/modules/locdit/unified_cfm.py:206 z = torch.randn_like(x1)`，
全程无 seed），`voice_desc` 文本前缀只是统计偏置。而 `app.py` 每个 LLM 分段
独立 POST 一次 `/synthesize` → **每个分段独立采样一个音色**。

量化基线（zero-shot、同库基座、4 段不同文本，ECAPA 段间余弦 vs 首段）：
**0.99 / 0.35 / 0.22 / 0.52**——后三段落在"不同说话人"带（自然语音实测
异人 0.06-0.44），即每次合成几乎换了一个嗓子。

## 2. 方案：参考克隆锚定 + LoRA

- **锚定**：启动时确定一个参考 wav，`build_prompt_cache(reference_wav_path=…)`
  编码一次，所有分段经 `_generate_with_prompt_cache(prompt_cache=…,
  streaming=True)` 复用同一 cache（音色 token 结构性隔离）。参考来源优先级：
  `VOXCPM_REF_WAV`（显式指定）> `VOXCPM_ANCHOR_WAV`（默认
  `data/voxcpm_anchor.wav`，持久化，删文件重摇）> 现场用模型合成固定校准句
  生成。锚定失败自动回退 zero-shot 并告警（服务不挂）。
- **流式不变**：仍是 producer/consumer + soxr.ResampleStream，首块延迟
  实测 78-92ms（与旧版持平）。
- **LoRA**：`from_pretrained(..., lora_config=LoRAConfig(r=32, alpha=32, …),
  lora_weights_path=…)`。**坑**：不传 lora_config 时包默认 r=8/alpha=16，
  形状不匹配会静默跳过全部权重——必须读 checkpoint 的 `lora_config.json`
  显式构造；服务端校验 loaded_keys 非空且 skipped 为 0，否则拒绝启动
  （静默无 LoRA 比崩溃更糟）。`VOXCPM_LORA_PATH=""` 禁用。
- **voice_desc 废弃**：克隆模式下参考音频说了算；app.py/前端删掉
  `tts_voice_desc` 设置与 UI 字段，服务端字段保留兼容但忽略。

## 3. 踩坑记录

- `_generate_with_prompt_cache` 流式 yield 的是 `(wav, tokens, feats)` 三元组
  （facade 的流式循环有解包，直调没有）——直接 `np.asarray(item)` 报
  "inhomogeneous shape"。统一按 tuple/裸数组两形态解包。
- 阈值校准：首次把判据定在 min≥0.60/mean≥0.70，实测 0.577/0.698 边缘
  FAIL。回看测量依据：自然同人下限 ~0.59、异人上限 ~0.44，表达力强的
  TTS 2-3 秒短段还有 ~0.1 的嵌入噪声——判据改为 **min≥0.55 / mean≥0.65**
  （相对 zero-shot 基线 mean 0.52 / min 0.22 仍分离清晰），非放水。

## 4. 验证（全部通过）

1. `voxcpm_consistency_test.py`：7 段（同文本×3 + 异文本×4）对锚点余弦
   **0.65-0.75，mean 0.711**，同文本三段 spread 0.044，首块 p95 83ms。
   对照 zero-shot 基线 mean 0.52 / min 0.22。
2. LoRA 加载：384 参数、0 skipped；health 报 `lora:true, anchored:true`。
3. e2e 6 轮：exit 0、无 STALL、turn_start 64、audio_chunk 311、
   0 pvad_reject；config_ws_test PASS（含"已删设置键被忽略"新断言）。
4. 回退演练：`VOXCPM_LORA_PATH=""` 重启 → 纯基座 + 锚定克隆照常出声
   （锚点 wav 是带 LoRA 时采的，回退后音色仍由参考锚定保持一致——
   这是特性不是巧合）。

## 5. 已知边界

- 情绪仍主要随文本走（锚定的是音色与基础风格）——符合预期。
- 锚点是一次随机采样，若不满意：删 `data/voxcpm_anchor.wav` 重启重摇，
  或 `VOXCPM_REF_WAV` 指定喜欢的声音。
- `_generate_with_prompt_cache` 是私有 API：voxcpm 钉 2.0.3，升级需回归。
- 试听样本：`logs/voxcpm_consistency/seg*.wav`（修复后）与
  `logs/voxcpm_consistency/zeroshot/z*.wav`（漂移基线）。

# 修改日志 — TTS 播放卡顿/打断风暴修复（nonidle 块 + 门控 fail-open）

**日期**：2026-10-29（同日，VoxCPM LoRA 之后）
**现象**：TTS 输出非常卡顿；卡顿时 UI 的 speaking/listening 圆圈不停跳变；
背景有噪声，但识别文本块里没有噪声文本、模型回复文本正常显示。TTS 输出本身
无噪声（用户确认）——指向系统框架某处存在 bug，导致 pvad/SoulX/LLM/TTS 都
正常但输出音频被频繁打断。

## 1. 根因链（已证实）

turn server（SoulX-Duplug）的语义 VAD 把播放期间的噪声/回声残留判为
nonidle → `vad_client.py` 对每个 nonidle 块返回 `[None]`（barge-in 信号）
→ `app.py` 里该会话**从未完成 ECAPA 注册**（旧逻辑要求 8s 环形缓冲里凑满
3s "语音块"——用户短话轮永远凑不齐，线上正是此条件）→ 说话人门控
fail-open → 每个 nonidle 块都触发 `interrupt()` → stop_audio 风暴 + 前端
abort 播放 + LISTENING/SPEAKING 跳变 + TTS 反复重启。
UI 跳变机制：前端收到 audio_chunk 置 SPEAKING、收到 stop_audio 置
LISTENING——打断风暴下两者每秒交替多次，即用户看到的"卡顿"。

## 2. 修改清单

### 2.1 `repo/dialogue_system/app.py` — 打断防御分层

1. **注册音频库（bank）**：每个通过门控且 ASR 非空的话轮，把 6s
   语音边界环尾存入 bank（上限 12s）。短话轮跨轮累积，第 2 轮前必完成
   注册——这是线上"永久 fail-open"的直接解。
2. **抢话迟滞**：连续 3 个 nonidle 块（480ms）才触发抢话判定；每个
   episode 只 interrupt 一次（`bargein_done`，`reset_interrupt` 重新武装）。
3. **播放中 fail-closed**：`playback_end`（audio_chunk 下发时估算的播放
   结束墙钟）未到时，不可验证的抢话（未注册，或 streak 音频不足 0.9s）
   一律拒绝——放过它就是卡顿 bug；真人会继续说，迟滞重触发后通过
   （晚 ~0.5s）。未在播放时维持 fail-open（无物可保护）。
4. **streak 身份评分**：抢话身份按触发它的 nonidle 块本身评分，不用
   环形缓冲（后者可能混入上一话轮，曾让回声起始段被评成主说话人）。
5. **圆圈状态门控**：播放期 LISTENING 不下发（circle_callback 包装）。
6. **打断时序崩溃修复**：新 TURN（非抢话）清空 `interruption_time` 后
   interrupted 分支 `None - float` 崩溃 → `(interruption_time or time.time())`。

### 2.2 ECAPA 窗口校准（决定 2.1 的全部窗口参数）

`scripts/ecapa_window_calib.py` + 临时探针的关键测量：

- **按块拼接的注册毁灭区分度**：自然连续 6s 注册下，1s 窗口同人
  0.55-0.70 / 异人 0.30-0.47 / 回声 0.26-0.47（0.5 阈值恰好落在缝隙）；
  拼接式注册把同人压到 0.17-0.56，与异人完全重叠 → 所有窗口改用**自然
  连续音频**（环尾 / 抢话 streak），bank 也存原始环尾。
- **静音填充垃圾分**：2.5s 窗口纯语音 cos 0.57；1s 语音 + 1.5s 静音
  0.23；纯静音 -0.08 → `_pvad_ring_tail` 对窗口做**边缘静音剪除**
  （内部停顿保留）。不做时话轮间隙的 blip 轮打分崩塌（实测同会话
  0.499 → 0.305 → 0.141 连续塌陷）。
- **0.5s 窗口无区分度**（同人仅 0.20-0.37）→ 抢话 streak 最低 0.9s。
- **同人漂移**：同一文件 27-33s 段对头部注册仅 0.33-0.50，恰在拒绝线
  附近 → **滚动再注册**：每个过门控的话轮都重注册。参考只会被"已过
  门控"的音频污染（bank 只存过门控话轮，环尾是刚评分通过的当前轮）。

### 2.3 `services/pvad_server.py`

`SCORE_MIN_SAMPLES` 16000→8000（0.5s）：第一次迟滞触发时 streak 只有
~0.5s 语音，1s 下限会在回声/噪声刚起时恰好 fail-open。

### 2.4 测试脚本

- 新增 `scripts/bargein_storm_test.py`：抢话风暴回归（注册 → -20dB 回声
  12s → rms 0.03 噪声 8s → 真人持续抢话）。回声阶段把 assistant 音频流
  按 0.1 增益回灌麦克风，复现浏览器 AEC 残留场景（修复前：自对话风暴）。
- 新增 `scripts/ecapa_window_calib.py`：注册方式 × 窗口长度校准表。
- 删除被取代的 `scripts/noise_chop_repro.py`。

## 3. 验证（全部通过）

1. `bargein_storm_test.py` **PASS**：回声 -20dB 0 次打断 / 15 次拒绝
   （修复前 12-15 次自对话风暴）；噪声 rms 0.03：0 次打断；真人持续
   抢话 2 次 stop_audio（迟滞 + 单次打断生效）；第 2 轮前完成注册。
2. `pvad_ws_test.py` **PASS**（13 检查全过；边缘剪除修复前因静音填充

3. `config_ws_test.py` / `pvad_service_test.py`：PASS。

   6→14；真人抢话拒绝（cos 0.43-0.498）全部经话轮路径 ~1s 内恢复打断。

## 4. 设计取舍（记录在案）

  （自适应说话人模型的通病）；每个话轮仍独立受阈值约束。

# 修改日志 — 播放中"突然沉默"修复（浏览器 AEC 破坏同人音色）

**日期**：2026-10-29（同日，打断风暴修复之后）
**现象**：用户确认打断风暴已修复，但实测浏览器对话中出现一段约 12s 的
"突然不说话"（系统沉默），随后自行恢复。日志定位（会话 135890e2，
19:18:18-19:18:31）：该时段每个用户话轮都被话轮门控以 cos 0.264-0.459
（阈值 0.5）拒绝——说话人确实是注册用户本人。

## 1. 根因（已证实）

**浏览器 WebRTC AEC 在播放期间破坏用户语音的音色**。用户在助手说话时
出声（重叠语音），浏览器回声消除把自身播放信号从麦克风信号中减除，
重叠段用户语音被连带扭曲 → ECAPA 余弦从平时的 0.55+ 跌到 0.26-0.46，
恰好跨过 0.5 阈值 → 话轮门控持续拒绝真人 → LLM 不响应（沉默）。
用户停止说话（无重叠）后余弦恢复 → "一会又好了"。

**为什么 WS 测试复现不了**：测试直连 `app.py`，麦克风音频不经浏览器
WebRTC 处理链，无 AEC 畸变。这是"线上行为与测试行为分叉"的典型场景。

**修复中发现的伴生问题**（实现播放期宽容时暴露）：回声话轮（echo）与
被畸变的真人话轮的 ECAPA 余弦区间**重叠**（回声 0.18-0.39 vs 畸变真人
0.26-0.46）——余弦在播放期**无法**区分二者；首轮实现里一段混窗（上一句
用户语音 + 回声）还让回声冒充用户通过门控并污染注册参考（随后真人只
得 0.166-0.253）。

## 2. 修改清单（`repo/dialogue_system/app.py`）

1. **播放期话轮宽容（turn gate leniency）**：`_pvad_turn_gate` 重构。
   播放期（`playback_end` + 1.5s 宽限）内，低于阈值**或不可评分**（此前
   不可评分走 fail-open 但不带标记，是回声起始段污染注册的旁路）的话轮：
   - 文本命中**自对话检查** → 照常拒绝（这是回声环路的死穴）；
   - 否则**放行但标记 lenient**——宽容通过的音频不入 bank、不滚动再注册
     （可能被 AEC 畸变/污染的音频不得移动注册参考）。
   空闲期话轮维持严格阈值（门控的本职：过滤助手话轮间的背景人声）。
   抢话路径不受影响（迟滞 + streak 评分 + 播放期 fail-closed 独立防护）。
2. **未注册时不设 lenient 标记**：宽容的首轮实现导致注册引导死锁
   （storm 测试复现：第 1 轮 bank 只攒到 2.1s < 2.5s，第 2 轮落在播放期
   被标 lenient 不入 bank → 永远注册不上）。未注册时没有参考可保护，
   bank 本身就是引导路径——照常入 bank；回声此时仍被自对话检查挡住，
   抢话路径被播放期 fail-closed 挡住。
3. **自对话文本匹配改为召回率**：`_pvad_selftalk_text` 用
   `difflib.SequenceMatcher` 匹配块总量 / len(查询) ≥ 0.6。原实现的
   子串匹配被一个错字击穿、整串比率被未匹配部分稀释（实测失败样本：
   回声 ASR"怎么又喊我婉儿呀" vs 助手原句"怎么又喊我"我儿"呀，是不是
   喊累了"——TTS→ASR 往返既错字又常只截到半句）。
4. **打分窗口按话轮切分**：`_pvad_ring_tail` 新增 `split_gap_s=0.6`，
   在最后一个 ≥0.6s 的内部静音处切断、只保留末段（当前话轮）。此前
   上一话轮完成后紧接的回声话轮会拿到混合二者的 4s 搜索窗，让跟在
   用户后面的回声"沾用户的光"过阈值（≥0.5 严格通过）→ 入 bank →
   污染参考。
5. `gap_chunks` 取整改为 ceil（int(0.6/0.16)=3 块=0.48s，与文档承诺的
   0.6s 不符）。

## 3. 验证（全部通过）

1. `bargein_storm_test.py` **PASS**：-20dB 回声 12s → stop_audio=1
   （单次起始话轮容忍）/ 14 次抢话拒绝；噪声 0 打断；真人抢话 2 次
   stop_audio；第 2 轮前完成注册（宽容-未注册引导修复回归验证）。
   首轮实现曾 FAIL：回声以混窗冒充用户过门控并触发 18s 错误注册。
2. `pvad_ws_test.py` **PASS**（11 检查全过；phase-3"被拒轮不进流水线"
   的统计窗口改为首个 reject 之后——播放期对非自对话低分话轮宽容
   放行是**新契约**，测试脚本同步注明）。
3. `config_ws_test.py` PASS；`e2e_web_test.py --rounds 2` exit 0：
   日志中出现 2 次播放期宽容放行（cos 0.419 等真人话轮，修复前这些
   会被拒）——正是线上"突然沉默"场景的等价复现被修掉的证据。

## 4. 设计取舍（记录在案）

- **播放期的人声冒充者会得到一次宽容响应**：播放期只有明确自对话被拒，
  空闲话轮才严格门控。接受理由：播放期无视真用户是门控能犯的最坏错误
  （本次线上 bug 即是）；冒充者代价是一轮多余回复，且其抢话仍受
  独立门控约束。
- AEC 畸变只发生在"用户在助手说话时出声"的重叠段；停止重叠后余弦
  自愈，无需额外恢复逻辑。

# 修改日志 — 移除播放期话轮宽容（用户决定：旁人得到回复不可接受）

**日期**：2026-10-29（同日，AEC 条目之后）
**背景**：上一条引入的"播放期宽容"（播放期低于阈值但非自对话的话轮放行）
上线后用户实测反馈：他人说话仍会显示到 UI 且模型尝试回复，不可接受。

# 修改日志 — 安静环境"幻听"话轮过滤（毛刺话轮丢弃）+ 快脑防编造约束

**日期**：2026-10-30
**现象**：用户实测环境安静、本人未说话，系统仍把"怎么样""是不是""怎么办"
"平时"这类短碎片当成真实话轮送进 LLM 并生成回复。

## 1. 根因（trace 诊断，session 04e38706）

1. **毛刺话轮**：TTS 播放期/刚结束后的低能量回声/噪声残留被 turn server
   判为 nonidle，1–2 chunk 后即产出"完整话轮"文本——该文本是 paraformer
   在低能量音频上的幻觉（trace 里逐条对上用户报的碎片）。抢话路径早有
   3-chunk 迟滞（`_BARGEIN_MIN_CHUNKS`），**话轮完成路径没有**——1 chunk
   的 episode 也能"完成"一个话轮。pvad 门控拦下了一部分（cos 0.32–0.47），
   但部分通过。
2. **快脑编造**（同 trace 顺带发现）：天气任务委派正确，但结果未回时快脑
   对追问编造了"大雨，温度18度，湿度85%，风速4米每秒"，还声称自己有定位
   能力；另在幻听话轮"不是。"上幻觉了一次"已取消"（未调 cancel_task，
   T1 继续在后台跑）。

## 2. 修改清单

### 2.1 `repo/dialogue_system/app.py`（毛刺话轮过滤，两轮迭代）

- **首版**（已废弃的判据）：`ChatSession.voice_run` 计当前 episode 连续
  nonidle chunk 数，complete-turn 时 `run < 3` 即丢弃（emit
  `pvad_reject kind=blip_turn`，前端走门控拒绝的同一清理路径）。
  **实测发现误杀**：turn server 常在音频已转 idle **之后**才发出话轮文本
  （风暴测试 turn1 的文本在语音结束后 ~3s 到达，`voice_run` 已被 idle 清零；
  长话语拆分出的尾段同样如此）——真话轮被当成 0–2 chunk 毛刺丢弃。
- **终版判据**：`ChatSession.last_sustained_voice_ts` 记录最近一次**持续
  语音**（≥3 连续 nonidle chunk，即抢话迟滞所信任的同一证据）的时间戳，
  nonidle streak 达到 3 时刷新。话轮接受 = `run ≥ 3` **或** 距最近持续语音
  < `_SUSTAINED_VOICE_WINDOW_S`(6s)。回声/噪声毛刺从不出 3 连续 chunk，
  打不开这个窗口；而无论文本多晚到，真语音的持续证据都在窗口内。
  首版与终版之间还试过"距上一被接受话轮 5s"锚点——首话轮无锚可依，废弃。
- 幻听话轮不触发 pipeline、不进历史、不注册 pvad、不打断播放。

### 2.2 `repo/dialogue_system/agent/runtime.py`（防编造 prompt 规则）

- `AGENT_SYSTEM_ADDON` 新增【重要】：后台任务结果交付之前，快脑完全不知道
  结果内容——禁止说出任何具体数据/事实，禁止声称定位、传感器等能力，
  只能说"还在查，稍后告诉你"。编造问题随 prompt 修复；"幻听话轮上的
  幻觉取消"随毛刺过滤消失（话轮本身被丢弃）。

### 2.3 `scripts/blip_turn_test.py`（新回归测试，7 项）

1–2 chunk 真语音能量毛刺不触发话轮且收到 blip_turn 拒绝；≥480ms 正常
短句照常触发；完整长句（含 turn server 拆分尾段）零误杀——第三组正是
首版过滤器翻车的场景，固化防回归。

## 4. 追记（同日 01:30）：过滤器上线即翻车，整体下线

1. **真人语音被误杀**：用户整句"喂，你怎么不说话了？""可以听到吗？"

   WebRTC 处理链（AEC/NS/AGC）后，turn server 的逐 chunk 状态
   nonidle/idle 严格交替**（约 50% 占空比，每条 suppressed 行间隔

2. **幻听无法用计数区分**：幻听碎片前的 episode 与真实语音同形态——

# 修改日志 — 抢话修复（"complete"触发话轮的宽限窗口）

日期：2026-10-30 · 现象：用户反馈"模型有点爱抢话，我话还没说完模型就开始抢话了"。

## 1. 根因（代码级定位）

turn server 状态机（`repo/service/model.py`）有两条"用户说完了"的出口：

- **wait 路径**：`<|user_incomplete|>` 后连续 `max_wait_num=5`（约 0.8s）
  静音才触发——**已经过静音确认**，可信。
- **complete 路径**：`<|user_complete|>` 预测一出现**立即**返回 speak，
  **零静音确认**。中文口语的句中停顿（想词、列举、语气缓冲）常被
  0.6B 模型误判为说完 → 助手抢话。

两条路径在 app 侧完全同形（都是 `segment` 为字符串），此前无从区分。

**连带伤害（agent_e2e_test 阶段 1 两次复跑一致 3 FAIL 的根因）**：
TTS 合成测试语音的句间停顿把一句话切成 4 个"complete"话轮，前 3 次
生成被下一话轮打断，向历史提交了截断的"好嘞，我这就去查…" assistant
残段——最终完整生成时模型看到自己"已经答应过去查"，于是只说受理
话术、**不再调 delegate_task**（阶段 2 无残段污染故委派正常）。

## 2. 修复（结构化：trigger 标注 + 宽限保持窗口）

- `repo/service/model.py` — 两个 speak 返回新增 `"trigger": "wait" |
  "complete"` 字段。
- `clients/vad_client.py` — speak 分支记录 `last_turn_trigger`。
- `app.py` — receive loop 在**发起 pipeline 时**（而非 worker 线程里）
  捕获 trigger（避免被下一个 vad.process 覆盖）；仅 complete 触发的
  话轮获得 `_TURN_GRACE_S = 0.9s` 宽限窗口，`_run_speech_pipeline`
  重构支持：
  - **保持期**：LLM 照常流式生成但全部进保持缓冲（LLM 首段本来就要
    ~1s，宽限期基本被生成延迟摊掉，感知延迟≈0）；不发 turn_start /
    text_response / 音频。
  - **复语中止**：持续语音（≥3 块，毛刺不触发）在窗口内出现 → 整个
    生成静默丢弃，不提交任何 assistant 文本（未说出的话不进历史）；
    用户续说的话轮经 llm_client groupby 与原消息合并成一个完整
    utterance。
  - **窗口平安过期**：held 分段经 `_flush_held()` 走正常播放路径。
    （首版实现的教训：held 文本最初直接累进 `message_to_add`，窗口过期
    后**从未播放**却进了 pending/历史——config_ws_test 复跑抓到：短回复
    在 0.9s 窗口内整体生成完毕时，客户端只收到 turn_start，无
    text_response/audio_chunk。held 分段必须单独存列表、flush 时逐段
    正常 emit。）
  - wait 触发 / 后台任务交付路径不设宽限；被打断且实际未说出任何
    内容时不再提交空 assistant 消息。

## 3. 验证

- `scripts/frc_mode_test.py` 同款"句中停顿"场景在 SoulX 路径的等价
  验证由 `agent_e2e_test.py` 覆盖（阶段 1 委派历史上正是被切分破坏）。
- `agent_smoke.py` 24/24；`config_ws_test` / `blip_turn_test` /
  `bargein_storm_test` 全 PASS；web + turn server 已重启加载新代码。
- agent_e2e_test 复跑（见下条日志）阶段 1 委派恢复。

## 4. 已知边界

- 宽限 0.9s 是"防抢话"与"应答快"的折中：真说完的用户多等
  ~0.3-0.9s（被 LLM 首段延迟部分摊掉）；话轮切分**减少**（一整句
  一次生成）反而降低总延迟与 token 浪费。
- 若用户 complete 触发后停顿 >0.9s 但确实没说完（罕见长停顿），仍会
  抢话——彻底解决需语义 EOT（frc 引擎即是）。

# 修改日志 — 任务状态按提及注入（慢脑工作期间自由闲聊）

日期：2026-10-30 · 需求："慢脑工作时语音前端可以跟用户闲聊其他主题，
只有用户提到时再同步慢脑的处理进度"。

## 1. 根因

`pipeline_worker` agent 分支**每轮无条件**注入 `agent_runtime.task_view()`
（"当前后台任务：T1（已运行 N 秒）：…"），快脑在后台任务存续期间的
**每次回复**（含闲聊、附和）都被提醒任务存在 → 模型反复汇报
"还在查/快好了"，无法自由聊别的。

## 2. 修改

- `app.py` — `_TASK_MENTION_RE`（查|任务|进度|结果|好了吗|出来|多久|
  搞定|完成|办到|找到|怎么样…）：用户话轮**提及**任务时才注入
  task_view；auto_cancel 触发时始终注入（取消确认需要事实依据）。
  正则刻意从宽：误报只是多注入一份（准确的）状态提示，漏报才是
  "查得怎么样了"却不知任务存在。
- `agent/runtime.py` — AGENT_SYSTEM_ADDON 对应改写为【闲聊不汇报】
  规则：明确"用户聊别的就陪聊，不主动提及后台任务与进度；只有用户
  问到才汇报"。

## 3. 验证

`agent_e2e_test.py` 阶段 2（慢任务期间闲聊"听音乐对放松有帮助吗"）
覆盖该路径：闲聊回复不再包含任务汇报措辞；任务保持 running、结果
仍在空档期交付。

## 4. 已知边界

- 注入门控是确定性的，但快脑对【闲聊不汇报】的服从是概率性的：
  E2E 实测偶发一次闲聊结尾主动补一句"对了，你刚才让我查的事我已经
  交给后台了"（历史里有委派对话，模型自行回忆）。此类越界只剩提示
  词约束兜底，若需硬保证须在文本出口做过滤。

# 修改日志 — FireRedChat 前端处理模式（turn_engine=frc，可切换）

日期：2026-10-30 · 需求："再加一个语音前端的处理模式，用 fireredchat
那边的架构，TTS 和 LLM 不变；当前 soulx 这套不动，前端可切换"。

## 1. 架构

新增 `repo/dialogue_system/frc_engine.py`（移植自
`full_duplex/scripts/frc_worker_integrated.py` 双 EOT worker）。会话级
设置 `turn_engine: "soulx"(默认) | "frc"`，Settings 面板实时切换；

frc 路径（LLM :6007/:6008 与 TTS VoxCPM2 完全共用，仅轮次判别不同）：

```

  持续 prob≥0.5 (3块) → 说话开始；连续 0.4s <0.5 → 静音结束

  P≥0.2 → 提交（判定耗时已超 min_delay 0.4s）；否则 hold 到 EOS+6.0s
  封顶提交；期间复语 → 取消待提交、话轮继续生长
提交 → FireRedASR :8010 整句转写 → 与 soulx 同一条 pipeline_worker
  （门控/历史/快慢脑/TTS 完全一致；不叠加宽限——双 EOT 本身就是
  防抢话机制）
```

新依赖服务（tmux `soulx` 新窗口 `ultravad` / `frcasr`，已入
`scripts/start_services.sh`，都在 GPU5 与 turn server 共卡）：
- **ultraVAD :8082**：`frc_services/ultravad/server.py`，eot_bench
  venv（唯一 transformers 4.57.1 环境）。注意模型加载 ~4 分钟（连带
  加载 fixie 文本预训练模型）；>20s 音频会 500（内部张量错误），
  引擎 ring 恰好 20s 封顶。
- **FireRedASR :8010**：`frc_services/asr`（uvicorn src.main:app），
  full_duplex/venv。端口避开 8000（soulx turn）与 8003（他人常驻
  proxy）；`load_audio` 依赖 ffmpeg 二进制，机器无系统 ffmpeg，
  PATH 里加 tempo conda env 的。转写含 PUNC+ITN 与填充词过滤。
- **:6007 新增 `/v1/score`**（移植 `frc_services/llm/
  qwen35_chat_server.py`）：首 token 概率打分（是/否 softmax），一次
  prefill ~60ms，与生成共用 GEN_LOCK 串行。

## 2. 实现要点（踩坑记录）

- **决策代际计数**：每次 end-of-speech 自增 `decision_gen`，HTTP 结果
  落地时校验代际——复语取消后再发的旧请求绝不能提交（最初用
  bool 标志，被"复语→新 EOS→旧请求晚到"序列击穿）。
- **pvad 概率滞后 ~1-2 块**（sidecar 异步 POST 回传），实际静音判据
  ≈0.6-0.7s，比标称 0.4s 保守——恰好增强防抢话，未补偿。
- **utterance 带前滚 2.5s**（onset 判定 + 概率滞后共 ~0.8s，防切头）；

- **切换引擎即时 reset**（update_config 里），防止切回时陈旧的
  待提交话轮突然触发。
- 前端无实时转写（FireRedASR 是整句后置转写，用户气泡在提交时才

# 修改日志 — VoxCPM2 文本正则化 + 轮次时序参数可配置 + 前端断线重连补强

**日期**：2026-10-30（下午）
**需求**：① VoxCPM2 疑似未开 text normalization（数字/符号直接进声学模型）；
② soulx 引擎 wait 路径的 `max_wait_num`（前端以对应毫秒展示）改为可配置；
③ complete 触发的保持窗口（宽限窗）改为可配置；④ 前端补断开重连能力。

## 1. 根因 / 背景

1. **TTS 数字念错**：VoxCPM2 门面 `generate()` 有 `normalize=True` 参数（内部
   走 `voxcpm.utils.text_normalize.TextNormalizer`，WeTextProcessing zh/en），
   但参考克隆模式走的 `_generate_with_prompt_cache()` **没有该参数**——数字、
   小数、单位直接进声学模型（"23.5度"按字面念、"0.6B"含混）。服务端必须
   自己先正则化再送生成。
2. **时序参数写死**：wait 路径确认块数 `max_wait_num=5` 钉死在
   `repo/config/config.yaml`，宽限窗 `_TURN_GRACE_S=0.9` 钉死在 app.py——
   不同用户/场景（急性子 vs 停顿多的说话风格）没法调。
3. **前端重连**：2026-10-26 已有一套完整自动重连（指数退避 500ms×2ⁿ 封顶
   5s、应用层心跳 8s/25s 半死强制断开、重连后重播 config_audio + 设置、
   connPill/connBanner UI）。本次为**补强**而非重建：缺网络层事件钩子
   （断网时干等退避计时器）、缺手动重连入口、后台标签页节流期间心跳失准。

## 2. 修改

### 2.1 `services/voxcpm_tts_server.py`（文本正则化）
- 新增懒加载 `TEXT_NORMALIZER` 单例（`TN_LOCK` 双检；WeTextProcessing 导入
  约 10s，只在首个含正则化需求的请求付出）。
- `synthesize()` 在既有空白清理后调用 `tn.normalize(text)`，参考模式与
  zero-shot 回退两条路径都覆盖。
- 环境开关 `VOXCPM_TEXT_NORM`（默认开，置 0 关闭）；`/health` 新增
  `text_norm` 字段。
- **降级策略**：正则化器初始化失败或单条文本正则化异常都只降级为原文合成
  （TTS 绝不因正则化问题拒服务）。

### 2.2 轮次时序参数全链路可配置（turn_wait_ms / turn_grace_ms）
- **turn server**（`repo/server.py`）：新增 `{"type":"config","session_id",
  "max_wait_num":N}` 控制消息（不回包——客户端 recv 循环严格一问一答）。
  服务端 1..50 块钳制；`session_config` 字典让覆盖值**穿越会话 GC 存活**
  （frc 模式期间 soulx 会话必被 60s GC，切回时自动恢复覆盖）。
- **模型链**（`repo/service/{model,engine,session}.py`）：`max_wait_num`
  作为可选参数随 chunk 传递（模型是全 session 共享的，旋钮不能挂模型实例
  上）——`state_predict` 里 `effective_wait = max_wait_num or config 默认`。
- **客户端**（`vad_client.py`）：`set_max_wait_num()` 存值并立即推送；
  `connect()` 后**每次重连重推**（对抗服务端 GC）。
- **web app**（`app.py`）：`DEFAULT_SETTINGS` 新增 `turn_wait_ms: 800` /
  `turn_grace_ms: 900`；钳制范围 160–3200ms / 0–3000ms（0=关宽限窗，
  即修复前行为）；会话建立、设置变更、frc→soulx 切换三个时机推送

# 2026-10-30（傍晚）：移除 realtime_note 注入（A/B 实测有害），addon 硬规则 + auto_delegate 兜底定型

## 1. 背景

经历了三个方案：addon 硬规则（prompt）、realtime_note（生成前注入 MUST-delegate
提示）、auto_delegate（生成后确定性兜底）。本条记录最终定型与依据。

## 2. A/B 实验（直连 :6008，完整 Elva 人设，每组 5 次）

| 方案 | 今天几号 | 现在几点 | 最近新闻 | 今天天气 |
|---|---|---|---|---|

| 新 addon + note（三种措辞） | 0/5 | 2/5 | 3/5 | 4/5 |

- **任何形式的尾部 user-role note 都有害**——模型把 note 当成要口头回应的内容，

# 修改日志 — 搜索工具切换 Tavily + 慢脑工具轮数上限 3 轮

**日期**：2026-10-30（晚）
**现象**：工具调用总是很慢。定位：web_search 的 DDG-html 端点在共享代理出口 IP
上间歇性被 bot 挑战，每次被挑战的查询要烧 5s 重试再绕百度；慢脑 MAX_STEPS=8
也让简单查询任务拖出投机性的 fetch_page 链。

## 1. 修改

### 1.1 `agent/tools.py` — web_search 主路切 Tavily
- **Tavily API 为主路**（key 从 `TAVILY_API_KEY` 环境变量或
  `/home/research/krisl/soulx/apikey.txt` 读取，每次调用时解析——key 文件后放
  也生效）；原 DDG+百度栈整体降级为 `_fallback_search`，Tavily 失败（无 key /
  配额 / 网络 / 空结果）时自动回退，任务不会死路。
- **Session 复用**（`_TAVILY_SESSION`）：省掉每次查询经代理的 TLS 握手，
  实测单次查询从 ~5s 降到 1.6-3.4s（首调含建连）。
- **不开 `include_answer`**：实测 +3s/查询且中文查询返回英文摘要（语言不匹配），
  结果 snippet 本身足够慢脑作答。
- 输出格式不变（编号 title/url/snippet），慢脑 prompt 无需改动。
- 工具 schema 描述同步更新。

### 1.2 `agent/slow_brain.py` — 工具调用轮数上限
- `MAX_STEPS` 8 → 4：循环最后一轮强制去工具出结论，即 **3 轮工具调用 + 1 轮
  强制作答**（用户要求"3 轮调用就一定要出结果"）。
- 系统提示第 2 条加入"你最多只有 3 轮工具调用机会"（提前告知，减少投机性
  抓取；轮内上限 MAX_CALLS_PER_ROUND=4 不变）。
- 最后一轮的带内提示（"工具调用次数已达上限…"）机制不变。

### 1.3 `app.py` — auto_delegate 碎片误杀修复（回归中发现）

  delegate_task（既知 ~10% 失效形态），auto_delegate 兜底却拿到**最后一个碎片**
