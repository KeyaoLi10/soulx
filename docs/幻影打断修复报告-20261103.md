## 1. 摘要

安静房间里、用户全程沉默，助手 TTS 播放被反复掐停，UI 同时浮现几个幻影汉字。根因是**昨天两个改动相乘**：

1. barge-in 迟滞下线（`_BARGEIN_MIN_CHUNKS` 3→0，d808980）：首个 nonidle 块零迟赫直接触发打断；
2. pVAD 默认 off（2026-10-30 起）：说话人身份门控不在环。

两者叠加后，扬声器回声 / AEC 残留的**单个** nonidle 块（160 ms）即可瞬间掐停 TTS。排查中还发现**第二条独立打断路径**：回声毛刺让 turn server 用 1-3 字幻觉文本 commit 一个假 turn，`pipeline_worker` 里的 `session.interrupt()` 同样掐停播放。

修复为**三层防御**（仅播放期、非 enforce 模式生效）：1.6 s 滑窗内 ≥3 个 nonidle 块才允许 barge-in；播放期 nonidle < 3 的假 turn 直接丢弃；正在播的内容与识别文本相似的自说自话过滤。真人抢话（4-8 块/回合）不受影响。新增 `playback_guard` 设置与前端开关。

## 3. 根因分析

### 3.1 根因链（已确认）

```
_BARGEIN_MIN_CHUNKS = 0   (d808980, 11-02 19:55 上线)
        ×
pvad_mode = "off"         (10-30 起默认，浏览器链路同人 ECAPA 分 0.15-0.57
                           不可用，见 soulx-pvad-default-off)
        ↓
单个 nonidle 回声块 → pvad_handle_bargein → gate 不在环 → _pvad_do_bargein
        ↓
TTS 播放被瞬间掐停
```

这两个改动**单独存在都不会炸**：阈值 3 时单块毛刺被迟赫拦下（10-30 上午的日志有大量 "suppressed (1 chunk(s) < 3)" 记录，说明当时该机制在正常工作）；pvad off 但阈值 3 时同样拦下。d808980 的"已知边界"一节其实预言了这个代价（"pvad_mode=off 时毛刺同样零迟赫触发……属该取舍的预期代价"），当晚就在真实环境兑现了。

### 3.2 为什么不能改回阈值 3

旧迟赫要求 **3 个连续** nonidle 块（≈480 ms）。但浏览器 WebRTC 处理后的真人语音 nonidle/idle 约 **50% 交替**，凑不齐 3 连块——这正是 10-30 把真人抢话推迟近半秒、进而下线迟赫的原因（同一结论当时已退役了 blip-turn 过滤器）。连续计数这个判别量对真人和回声**都不成立**，恢复它只是把 bug 换回上一个 bug。

### 3.3 两条独立的打断路径

复现测试中发现掐停播放的路径有两条，必须分别堵：

| | 路径 a：回声块直接打断 | 路径 b：幻影 turn |
|---|---|---|
| 链路 | nonidle 块 → `pvad_handle_bargein` → `_pvad_do_bargein` | 回声毛刺 → turn server 以**幻觉文本** commit turn → `pipeline_worker` 中 `session.interrupt()` |
| 签名 | 早期掐停，Ratio 0.35-0.37 | 中晚期掐停；出现 1-3 字假用户消息 |
| 幻觉文本实例（实测捕获） | — | `'没事儿。'` `'急。` `'及。'` `'没。'` `'赶紧的是。'`（paraformer 对回声的典型短幻觉） | 
| 对应防御 | 层 1（滑窗门控） | 层 2（episode 计数丢弃）+ 层 3（文本过滤） |

注意路径 b 的幻觉文本是**凭空产生的**（不匹配任何正在播的内容、长度在自说自话过滤的 4 字下限以下），所以层 3 的文本匹配对它无效——这是层 2 必须存在的原因。

### 3.4 修复过程中发现并堵掉的一个回退漏洞

初版层 2 带 `sustained_recent` 回退（`last_sustained_voice_ts` 后 6 s 内放行 turn，本意是别误伤刚确认过抢话的用户）。实测 00:23 run 证伪：一次被确认的响亮回声也会刷新该时间戳，4 秒后的毛刺假 turn `'赶紧的是。'` 从这个窗口里溜了进来。**修复版本在播放期丢弃分支刻意不用该回退**（打断后场景由层 3 的 `recent_interrupt` 窗口覆盖，语义更严：要求文本确实像自己的话）。

## 4. 设计：占空比判别

核心观察是把"回声毛刺"和"真人语音"在**块级统计**上分开：

| 信号源 | 每回合 nonidle 块数 | 窗口内密度 |
|---|---|---|
| 回声/AEC 残留（线上实测、复现测试） | 1-2（episodic 毛刺，~2.2 s 一发） | 1.6 s 窗内 < 3 |
| 真人语音（浏览器 WebRTC，50% 交替） | 4-8（任何值得成句的话） | 1.6 s 窗内 ≥ 3 |

判别量取**滑窗占空比**（1.6 s 窗内 nonidle 计数 ≥ 3）而非连续计数：对 50% 交替的真人语音，10 块窗内期望 ~5 个 nonidle，必过；对 1-2 块的毛刺必拦。窗口取 1.6 s ≈ 10 块，是"真人凑满证据只损失约 1 秒（且整个抢话 episode 只损失一次）"与"毛刺永远凑不齐"之间的平衡点。

所有防御**仅播放期生效**（`now < playback_end`，含 1.5 s 收尾宽限），非播放期保持零迟赫快路径不变；pvad enforce 模式跳过（它有自己的更强 fail-close 检查）。

## 5. 改动明细

### 5.1 `app.py` — 三层防御

**会话状态**（`app.py:202-211`）：`bargein_times`（`deque`，滑窗时间戳）、`episode_nonidle`（整回合计数）、`last_nonidle_ts`（回合分隔用）。与 `bargein_streak` 的区别：跨 idle 间隙存活，专为 50% 交替的真人语音设计。

**常量与开关**（`app.py:382-407`）：

```python
_PLAYBACK_BARGEIN_WINDOW_S = 1.6   # evidence window (~10 chunks)
_PLAYBACK_BARGEIN_NONIDLE = 3      # nonidle chunks needed inside it

def _playback_guard_active(session):      # playback_guard 设置 AND 非 enforce
def _playback_bargein_deferred(session):  # 播放中 AND 证据不足
```

**层 1 — 播放期 barge-in 门控**（接收循环 nonidle 分支，`app.py:1255-1263`）：每个 nonidle 块记时间戳进滑窗，`pvad_handle_bargein` 前检查 `_playback_bargein_deferred`——证据不足时不打断也**不清 streak**（证据在积累），凑满 3 块自动放行。真人只损失约 1 秒、只损失一次。

**层 1 的事件与日志**：压制时打 `"transient barge-in suppressed (N unconfirmed chunk(s), M in 1.6s window)"` 并发 `bargein_deferred` 事件；未确认 streak 化入真 turn 时发 `bargein_deferred {"resolved":"turn"}`（前端据此不撤已确认的气泡）。

**层 2 — 幻影 turn 丢弃**（接收循环 speak 分支，`app.py:1341-1368`）：turn commit 时若仍在播放（含宽限）且 `episode_nonidle < 3`，丢弃该 turn：

```python
if (playing and _playback_guard_active(session)
        and session.episode_nonidle < _PLAYBACK_BARGEIN_NONIDLE):
    # NOTE: deliberately NO sustained-voice fallback here ...
    emit_to_room(client_id, "selftalk_drop", {"reason": "blip", ...})
    session.episode_nonidle = 0
    continue
```

日志 `"playback blip turn dropped (N nonidle chunk(s) in episode < 3): '...'"`。回合计数在 2.5 s 干净静音后重置（毛刺与毛刺之间不累计误伤）。

**层 3 — 自说自话文本过滤**（`pipeline_worker`，`app.py:804-814`）：对播放期 **或** 打断后 1.5 s 内（`recent_interrupt`——interrupt 会清零 playback_end，单看 playback_end 会漏掉刚打断的窗口）commit 的 ASR 文本跑 `_pvad_selftalk_text`（vs 正在播的 assistant 分段 / pending message / 近期历史，SequenceMatcher 召回 ≥ 0.6，4 字归一化下限）。命中则 `selftalk_drop {"reason":"selftalk"}` 并 return。

层 2 与层 3 的分工：层 3 抓**真回声转写**（文本确实像自己刚说的话），层 2 抓**短幻觉**（低于 4 字下限、与内容无关的凭空文本）。二者都不命中、而且回声确实稀疏的 turn，才可能是真人——放行。

### 5.2 `settings.py` + 前端 — `playback_guard` 开关

- `DEFAULT_SETTINGS["playback_guard"] = True`；`sanitize_updates` 尾部 bool 特判（`settings.py:140-141`）。关闭即恢复 d808980 的零迟赫裸行为（排障/对比用）。
- `frontend/index.html`：Voice Engine 面板新增 "Playback echo guard" 勾选框（含说明文案）；`frontend/script.js`：`currentSettings()`/debounced send 接线、随 frc 引擎一起置灰（SoulX 引擎专属）、`selftalk_drop` 事件处理——移除已冒出的假用户气泡 + 闪现提示"已忽略回声（识别到的是我自己的声音）"。

**实现注记**：没有复用 `pvad_reject` 事件——其前端 handler 对 `cos:null` 会执行 `cos.toFixed(2)` 直接崩（既有潜在 bug，本次绕开未修，已在日志记录）。

## 7. 已知边界

1. **播放期超短命令会被忽略**：整回合 nonidle < 3 的真人语音（如播放中只说一个"停"字）与回声毛刺在该判别量下不可区分，会被层 2 丢弃。要打断请说完整短语（"停一下"、"等一下"自然过窗）。
2. **密集干净回声仍可晚期打断**：合成干净回声若被语义 VAD 持续认成语音（≥3 in window），会通过门控——表现为 Ratio 0.91-1.00 的晚期掐停，与线上 bug 的早期签名（0.35-0.37）不同。真实浏览器 AEC 削掉回声的线性成分，线上读作 1-2 块毛刺，故此为合成侧边界。兜底：戴耳机（物理消除），或开 pvad enforce。
3. **防御事件计数天然波动**：VAD 挂钩悬崖（6.2）使线上毛刺注册率不稳定，某次会话看不到 suppressed/dropped 日志不代表防御失效——主判据是"无早掐"。
4. `pvad_reject` 前端 handler 的 `cos:null` 崩溃是既有独立 bug，本次绕开未修。

## 补遗：生成期幻影打断（当晚 01:01 第二次线上事故）

**现象**：修复上线后用户再测——第一句"喂，你好，可以听到吗？"说完、
显示正常，随后 UI 里这句话**突然被替换成"是。"**（会话 338b1765）。

### 根因：三层防御只覆盖了播放相

昨晚的修复把所有防御都键在 `playback_end` 上，但 **turn commit 到首个
TTS 音频之间还有 1-2 s 的生成窗口**（LLM 流式产出 + TTS 合成首段），
期间 `playback_end` 是陈旧的：

| 防御 | 生成窗口内的状态 |
|---|---|
| 层 1（滑窗门控） | 失效——毛刺 nonidle 块直接 `_pvad_do_bargein` → `session.interrupt()`，无条件杀死在途生成（此刻没有任何可打断的播放） |
| 层 2（episode 丢弃） | 失效——`playing = now < playback_end` 为假，幻影 turn 照常跑 pipeline，"是。" 写入 LLM 历史 |
| 层 3（自说自话） | 失效——同上，窗口判断不含生成相 |

前端侧还有一个独立的**吞句机制**：活动用户气泡在 commit 时没有冻结
（`turn_start` 要等 pipeline 开口才发），幻影 turn 的 partial/最终转写
经 `handleUserTranscription` **原地覆盖**了真实句子——用户看到的"被
吞"直接由它造成，与幻影 turn 后续是否跑完无关。

### 修复

1. **`_reply_in_flight(session)`**：`gen_in_progress OR now <
   playback_end + 1.5s`——统一"在途"窗口（生成 + 播放），三层防御
   全部改用（先例：`frc_engine.py` 早已用这一对条件）。
2. **`_begin_generation()` 在接收循环 commit 时刻调用**：原来
   `gen_in_progress` 要到 pipeline_worker 建好 LLM 生成器后才置（agent
   模式 ~0.5 s 空档），round 2 实测毛刺 barge-in 正好钻这个空档杀死了
   在途生成。配 `gen_serial` 序号：被打断的旧 pipeline 的 finally 不
   得清掉接替者的标志（顺带修掉一个既有的重叠竞态）。`_frc_commit` 与
   agent 交付路径同样接入。
3. **commit 时 `bargein_times.clear()`**：已 commit 话语的 nonidle
   证据不得为 ~0.8 s 后的毛刺背书——round 3 实测毛刺骑着 seed 语音
   未过期的窗计数凑满 3 过了门限，结构与 01:01 线上事故完全一致。
4. **惰性 burst 重置**：`episode_nonidle` 从"idle 分支 2.5 s 定时清
   零"改为"nonidle 分支里距上次 nonidle > 1.6 s 才清零"。原实现下
   2.2 s 节奏的重复毛刺会跨毛刺累计过 3 门限（round 1 发现的真漏洞）；
   改惰性后真人话轮的证据可扛任意 `turn_wait_ms`（上限 3200 ms）的
   等待静音。

## 补遗二：毛刺来源取证与前端判别量分析

（对应问题：生成期那口毛刺物理上从哪来？换传统 VAD 或 pVAD 能否解决？）

### 1. 生成期毛刺的物理来源：话尾呼吸，不是回声

事故会话 338b1765 的关键时间线：

```
01:01:38,965  barge-in confirmed                     ← 用户开口"喂，你好…"
01:01:40,203  ASR result: 喂，你好，可以听到吗？      ← 真实话轮 commit
01:01:40,736  barge-in confirmed                     ← 毛刺：commit 后仅 0.5 s
01:01:41,695  ASR result: 是。                       ← 毛刺凑成的幻影 turn
01:01:42,622  LLM Chunk: 哎，我在呢…                  ← 真实回复照常生成
```

**排除回声**：毛刺落在 40,736，而回复的 TTS 音频要到 ~01:01:43 才开始
播——生成窗口内助手完全静默，扬声器回声/AEC 残留（昨晚播放期事故的
成因）在这里不成立。

**真实来源是说话人自己的话尾**：说完一句升调问句后 0.5 s 正是自然
呼气/换气/口腔余音的位置，且同一会话里是可重复的模式而非孤例：

```
01:01:53,898  ASR result: 呃，给我。    ← 同样出现在第二句 commit 后 0.5 s
```

机制链：呼气（低频气流噪声）→ 浏览器 WebRTC 在话尾 AGC 增益尚未
回落、噪声抑制 toggling，把这段近静音整形出能量 → SoulX 语义 VAD 的
挂靠呈陡峭悬崖（同一信号或挂或不挂，见 6.2 校准记录），这次挂上了
1-2 块 nonidle → turn server 将短促发声判为完整话轮 → paraformer 对
近静音气流**幻觉**出短汉字。幻觉家族（两次事故累计捕获）：
`'没事儿。' '急。' '及。' '没。' '是。' '呃，给我。'`——均不对应任何
真实说过的话。

这类话尾呼吸毛刺每次说话都可能有，以前没炸多是因为 VAD 挂靠是概率
性的、或恰好落在防御覆盖窗口内——回归测试 phase 0 专门在生成窗口灌
毛刺即为此固化。

### 2. 为什么传统 VAD / pVAD 都解决不了

**传统（能量）VAD**：这个毛刺的本质是"有能量的非语音"。呼气本身
就有真实声学能量，还叠加 AGC 话尾放大，能量/过零率判别量上与语音
不可区分，触发只会比语义 VAD 更确定。语义 VAD 反而是现有前端里最好
的一道——至少有挂靠悬崖，有时直接不理会呼吸，换传统 VAD 是判别力
降级。（理论上呼气有无基音/无谐波结构的声学签名，"有声性"判别器可
以分开，但那不是现成传统 VAD 提供的能力，需要自建且收益不如下述
占空比判别。）

**pVAD（ECAPA 身份门控）**：方向对（身份判别）但在这条浏览器链路上
已被实测证伪——

1. 同人 ECAPA 分 0.15-0.57 vs 阈值 0.5，阈值卡在真人带正中间
   （2026-10-30 默认 off 的原因，见 soulx-pvad-default-off）：enforce
   会慢性拒绝真人本人（"30 秒后一直不说话"事故）；
2. 呼气片段仅 160-320 ms，ECAPA 不可评分 → 播放期外 fail-open 照样
   放行；且呼气就是**本人**发出的，即使可评分也未必低于本人阈值。

### 3. 有效判别量：占空比，以及可选的后续加固

毛刺 family 里有三种信号要同时分开，各自成立的有效判别量不同：

| 信号 | 有效判别量 | 对应防御 |
|---|---|---|
| 回声/AEC 残留 | 文本层（自说自话召回 ≥0.6） | 层 3 |
| 话尾呼吸 → ASR 幻觉 | **时长/占空比**（1-2 块 vs 真人 4-8 块） | 层 1/2 |
| 真人抢话 | 上述两个都必须放行 | — |

呼气毛刺唯一稳定的物理签名是**短**——无论能量多高、文本幻觉成什么
字，它凑不出 3 个 nonidle 块。滑窗占空比门控因此比换任何前端 VAD 都
可靠：它不依赖"认出这是呼吸"，只依赖"呼吸长不成一句话"。

若要再加一道保险，收益最大的两个方向都不是换 VAD：

- **ASR 置信度**：paraformer 对幻觉 token 的置信度通常显著低于真实
  转写，低置信短文本可按分数丢弃；
- **turn server 侧最短语音时长**（<480 ms 不许 commit）：等价于把
  app 层的 episode 计数下沉到前端，效果相同且省一次 ASR 调用。

## 补遗三：「刚才」/「对对对」毛刺 ASR 定位与会话时间线工具（2026-11-04）

用户 16:31 实测（会话 `1efc5af4`）复现两类毛刺转写，诉求是先分析清楚、
不改对话逻辑。结论如下，全部有日志/代码证据。

### 1. 「SoulX 的 ASR」还是「paraformer」——伪二分，是同一个

链路上只有一个转写引擎。web app 自身不配 ASR（`app.py` `asr = None`，
pipeline_worker 对字符串 segment 直通），全部文本都出自 SoulX turn
server（:8000）：其内部的 cascade ASR **就是 paraformer**
（`repo/service/model.py`，`config.yaml` `model_name: paraformer`）。
SoulX-Duplug 0.6B 语义 VAD 只负责**话轮边界**判定；它输出的
`asr_buffer`（流式 partial）和 commit 时的 `text`（最终转写）都是内嵌
paraformer 的产物。所以「刚才」「对对对」都来自同一个 ASR，区别只在
**是否 commit**。

### 2. 「对对对。」——已提交，已进 LLM

时间线（新工具还原，相对会话起点）：

```
+100.4s turn   可是你不应该。          ← 真实语音被中途拆句（见 §4）
+101.9s turn   知道我现在在哪吗？
+102.6s suppressed (n=1, 窗内1)
+102.8s suppressed (n=1, 窗内2)
+103.0s barge-in confirmed            ← 第 3 个 nonidle 块，恰好过门限
+104.1s turn   对对对。
+104.9s chunk  哈哈，放心，后台一查天气就能确定啦…  ← 为它生成的回复
```

- **层 1/2 合法放行**：三个 nonidle 块（16:31:14,988 / 15,189 / 15,372，
  约在上一问句结束后 0.7s 起）恰好满足「1.6s 滑窗内 ≥3」——这是与
  「是。」/「呃，给我。」（1-2 块）同族但**更密**的话尾残留，最可能是
  一串轻笑/密集呼吸，被 paraformer 幻觉成节奏性的「对对对」。
- **层 3 跳过**：「对对对」3 字 < 自说自话过滤的 4 字归一化下限。
- **确进 LLM**：`llm.add_message(user)` 后生成了「哈哈，放心…」回复；
  后续 llm groupby 又把它并入连续 user 消息。

即：这不是防御失效，而是占空比判别量的**边界样本**（3 块恰好过线），
正落在补遗二「未来加固」预告的位置——ASR 置信度（幻觉 token 置信度低）
或 turn server 侧最短语音时长都能收掉它。本次按用户要求不改。

### 3. 「刚才」——未提交，未进 LLM，只污染 UI

它是 turn server 流式 `asr_buffer` 的 **partial**：`vad_client.process()`
在 nonidle 块上 emit partial → `user_transcription` 无 `final` 标志 →
只写前端实时气泡，从不触发 pipeline、从不进 LLM。它说完整句话前呼吸
消退、状态机回 idle，partial 就蒸发。

**当时的观测盲区**：`transcription_callback` 只发事件不落日志——
「刚才」何时出现、持续几个 partial，web.log 里完全无痕，本次取证只能
靠推断。已补一行观测日志（`ASR partial: …`，turn server 已去重，每
个**变化**的 partial 一行），属纯观测、零行为改动。

### 4. 附带发现：真实语音被中途拆句

「可是你不应该。」+「知道我现在在哪吗？」是同一句话被 turn server
在句中 commit 拆成两段（`turn_wait_ms` 800ms 内的停顿即触发）。两段都
进了 LLM 历史（groupby 兜底合并），对话未受实质影响，但**commit 的
trigger 类型（wait/backchannel/…）没有落日志**——又一个观测盲区，留待

### 6. 时间线音频叠加（同日追加）

时间线再进一步：服务端把每个会话的**麦克风**（重采样后 16k，即 turn
server 实际看到的信号）与 **TTS 播放流**（24k）各录成裸 PCM
（`logs/audio/<sid>.{mic,tts}.pcm` + 首帧时间戳 sidecar），sessions.html
在泳道下方画两条与之共享时间轴的波形，点击任意位置从该处试听，红色
播放头跨泳道/波形联动。毛刺到底是呼吸、回声还是真实语音，从此一听
便知，不再靠推断。

- 服务端点 `/api/logs/sessions/{sid}/audio/{kind}` 返回带 Range 的 WAV
  （与日志 API 同密钥门控——录音是个人数据）；`SOULX_AUDIO_RECORD=0`
  可关；单会话单流上限 96 MiB，保留 3 天（新连接时触发清理）。
- 录音是纯旁路 best-effort：写失败只告警一次，绝不阻塞或中断对话主
  路径。回归验证：`playback_echo_test` 全 PASS，麦克风录音 41s 与测试
  全程吻合、语音段位置与 seed 阶段一致，TTS 录音可解码、幅值正常。
- 已知边界：录音只覆盖上线（17:29）之后的会话；空闲重连的空会话也
  会录（默认隐藏，不影响）；音频在选中会话时一次性拉取，live 模式下
  播放中新增的音频需重新选择会话才会加载。

**2026-11-05 修复**：上线后"看得见波形、听不到声音"。根因是
`decodeAudioData(buf)` 按 Web Audio 规范会 **detach 传入的
ArrayBuffer**，之后再 `new Blob([buf])` 得到 0 字节 blob——波形用
解码后的 buffer 绘制所以一切正常，`<audio>` 元素却拿到空文件，任何
Range 请求 416（`ERR_REQUEST_RANGE_NOT_SATISFIABLE` →
`MEDIA_ERR_SRC_NOT_SUPPORTED`），且被 `play().catch(() => {})` 静默
吞掉。该功能在 Chrome 上从未真正出过声。修复：**先建 blob 再解码**；
`play()` 失败改为 console.warn 不再吞。headless 复现验证：PLAY OK、
seek 精确（点击处 ±0.6s）、播放头联动正常。同修一个次生问题：波形
原先是把整段录音**拉伸铺满**泳道时间轴（录音不覆盖全会话时与事件
错位、点击中段会 seek 到文件末尾），改为逐像素按会话时间映射采样，
无录音区域留白——reconnect 复用 sid 的会话（事件跨度远大于录音时
长）不再误导。

**同日追加：双轨同步还原现场**。波形提示行新增「双轨同步 · 还原现
场」开关（localStorage 持久化）：勾选后点击任意位置，麦克风与助手
播放流从同一会话时刻**同时出声**——打断、抢话、回声的原貌一听便
知。每路各自映射到自己的录音区间（区间外静默、时钟走到自动加入退
出，两路起始数秒的错开由会话时刻统一吸收）；会话时钟以"正在播的
那一路"为基准、0.25s 漂移校正，两路都在空白区时由墙钟推进接续。
headless 实测两路会话时刻相差 21ms。

**再追加：TTS 录音的时间轴是压缩的——run 索引保真**。双轨上线当天
即暴露：tts 波形里轮间完全没有 idle，回放无法还原现场。两层根因：
其一 `_SessionAudio` 按发射时刻 contiguous 追加，段间/轮间静默不产
生字节；其二发射节奏 = 生成速度（VoxCPM2 实测 RTF≈0.36：3.94s 发出
10.88s 音频），发射时刻≠播放时刻——间隔检测必须锚在**播放时钟**上。
修复（重启 web app 生效）：sidecar 升级为
`{"start", "rate", "runs": [[字节偏移, epoch, 截断秒?], ...]}`，新
run 的判定是写时刻越过「run epoch + 已写音频时长 + 0.5s」（与
`playback_end` 公式同构——浏览器缓冲会桥接生成间隙，只有真·听觉静
默才断 run；mic 实时节奏下退化为普通写间隔检测）；每条回复管线首
次发射强制开新 run；管线被打断时把最后一个 run 的可闻长度截到打断
时刻（`mark_cut`，带竞态守卫），发射跑在播放前面、缓冲里未播出的字
节不再被当作"响过"；重连/重启采纳既有 sidecar 续算，legacy 录音
回退单 run 不透明映射。前端 `tToLocal`/`localToT` 分段映射取代线性
`t − start`，cut 后的字节与 run 间空隙留白。e2e 三轮真会话：29.4s
语音分布在 118.7s 墙钟里，轮间 idle 7.6/17.5/8.1/5.1/51s 全保留；
headless 验证 gap 点击墙钟携带、run 内双轨起播、cut 注入 past-cut
静默 mic 照播、旧会话回退逐位等价。**重启前的旧 tts 录音仍是压缩
的**（legacy 回退），仅新会话起保真；run epoch 比实际可闻时刻早一
个客户端缓冲延迟（~0.2s）。

## 补遗四：毛刺根修——turn server 侧结构性门控（2026-11-04）

前三个补遗把毛刺的来源（话尾呼吸/轻笑）、ASR 幻觉路径（paraformer 对
合成噪声种子幻觉出「对对对」「刚才」）和观测工具都补齐了，但防线仍全部
在 app 侧「事后否决」。用户的进一步诉求是**结构性预防**：呼吸毛刺根本
不该进得了 turn server 的状态机——「基本没什么额外声音，按理说 VAD 应该
能解决」。

### 1. 根因：为什么「按理说能解决」却没解决

turn server 每 160ms 对音频块做一次话轮状态判定，问题出在三个环节的
组合（`repo/service/model.py`）：

1. **`speech_detected` 无条件闩锁**：argmax 判为 nonidle 的**第一个**块
   就把会话置为「检测到语音」，没有任何置信度、能量或时长要求。呼吸块
   只要恰好赢了 argmax（哪怕 7 类 softmax 里只拿了 0.98 之外的低置信），
   幻影话轮就开始了。
2. **argmax 丢弃了全部置信度信息**：模型其实输出了 7 个状态 token 的
   完整 logits，代码只取最大者。模型「 confidently 错」与「confidently
   对」在下游不可区分。
3. **识别缓冲里混着合成噪声种子**：`reset()` 会给 ASR 缓冲预填 1.6s /
   3.2s 合成噪声当底噪。纯噪声 + 近静音正是 paraformer 幻觉短文本的
   最爱——所以毛刺 commit 出来的不是空串而是「对对对。」。

App 侧三层防御（滑窗/假 turn 丢弃/自说自话过滤）拦得住 1-2 块的回声
毛刺，但「对对对」3 块恰好过滑窗线、3 字又低于自说自话过滤的 4 字下限
——边界样本必然存在，事后否决永远在追着补。**修复必须前移到 latch
之前。**

### 2. 设计：turn server 侧五道门（A / C′ / D / E / F）

| 门 | 位置 | 作用 |
|----|------|------|
| A 概率门 | `_state_predict`，decode 后、mistake 计数前 | 未 latch 期 argmax=nonidle 但 7-way softmax p(nonidle) < 0.5 → 降级 idle（**同时覆写 `pred`**——下一步输入 embed 由它构成，KV 叙事须与机器动作一致） |
| C′ RMS 门 | 同上，A 之后 | 未 latch 期块 RMS < 0.01 → 降级 idle。**不复用** `far_field_threshold`（旧分支会 reset 重播种子破坏流连续性） |
| D 卡死不信任 | mistake 仲裁入口 | nonidle 连续 ≥5 块且本话轮 cascade 文本为空 → 降级 idle 清零计数，不强制仲裁、不 reset（慢 ASR 真人 onset 仍存活） |
| E 空文本守卫 | wait/complete 两个 commit 点 | recognize 出空文本 → reset 返回 idle 而非 speak |
| F 种子裁剪 | 所有 recognize() 输入 | 把 1.6s/3.2s 合成噪声种子从识别输入中剔除（噪声里不可能有语音，零风险），让 E 更多命中 |

**真人弱 onset 安全性**：每个未 latch 的 nonidle 块只要满足三条件之一
（p ≥ 0.5 / RMS ≥ 0.01 / ASR 已见到词）就照常 latch——门只挡三个全不过
的块。

**明确否决**：最短连续 nonidle 计数门。实测真人 WebRTC 语音 ~50% 占空比
**永远不连续 3 块 nonidle**，而「对对对」毛刺恰是 3 连块——连续计数是
反向判别量，先杀真人。理由注释保留在 `config/config.py`。

App 侧三层防御全部保留：扬声器回声能量足、置信高，服务器门控管不了
回声，播放期滑窗仍是回声的正解；对呼吸毛刺则从「主力」退为「冗余」，
观察一周后另行清理。

### 3. Stage 0 标定：置信度不可信，能量可信

门限不是拍的。Stage 0（门全关、纯测量）回放标定语料（真人 onset n=8 +
合成毛刺 12 组 + 整句对照）得到分布：

- 真人 onset：p_nonidle 0.974–0.999，RMS 0.019–0.140
- 毛刺块：p_nonidle **0.985**，RMS **0.005**（另有一次静音误触发 p 0.933 / RMS 0.000）

即**概率没有分离度**（模型错的时候一样自信），**RMS 分离干净**。因此
概率门 0.5 只作安全网（真人从不会接近），RMS 门 0.010 承担分离：比最弱
真人 onset 低约 2 倍、比毛刺高约 2 倍。标定数据留在
`results/blip_gate_replay/`。

### 4. 回归教训：D 门的两版错误形态

D 门（mistake 路径不信任）首版复用 `max_mistake_num=3` 做阈值、降级了事，
连出三个回归，最终形态是两次结构修正的结果：

**教训一：一个 knob 不能承担两个角色。** mm=3 同时是「仲裁节奏」（paraformer
文本滞后音频 1-2 块，多句独白期间无文本 nonidle 连续 3 块经常达成 → 强制
complete/incomplete 仲裁，这正是基线在句间产生 commit 的机制）和「D 的怀疑
线」（需要 ≥5：480ms 真人短句在第 3 块撞线时文本还没到，mm=3 的 D 会误杀
真人短句）。首版把 mm 升到 5 想躲开误杀，结果仲裁节奏被饿死——模型把句间
停顿一直判 nonidle、wait 路径凑不齐 5 连 idle，**整句语料第 2、3 句永不
commit**。修正：D 拿独立 knob `mistake_no_text_num=5`，mm 回到 3。

**教训二：降级不能「消耗掉」nonidle→idle 迁移。** D 触发时把当前块降级为
idle，但真人短句的文本 1-2 块后才到——而状态机里 commit 只挂在迁移和
wait 路径上，迁移已被 D 提前用掉，wait 路径又没武装，文本到了无人提交，
短句照样死。修正：**D 降级的同时武装 wait 路径**（`monitoring_wait_silence
= True`）。ASR 本来每块都跑（`_asr` 由 LLM 的 eos 预测门控、与话轮状态
无关），所以文本晚到时 wait commit 照样接得住；毛刺则在这条路上被空文本
守卫（E）收掉。若模型在静音上卡死 nonidle、wait 永远等不到 idle 块，第二
次 D 直接升级为整场 reset，保证会话不会挂死。

两个阈值、两个回归的来龙去脉都写在了 `config/config.py` / `config.yaml`
的注释里，防止后人再合并它们。

顺带的认知修正：full_utterance 的断言从「≥3 次 commit」改为**内容覆盖**
（三句关键词都必须落在某个 commit 里、commit 不得为空）。commit 的确切
次数和切分点本来就会随 KV 叙事的任何扰动漂移——种子裁剪（F）改变了
paraformer 的文本时序，文本 token 又是 LLM 输入的一部分，切分点必然移动。
把机制的快照写进断言只会每次改门都误报；断言该锁的是需求（语音不丢、
无幻影），不是实现细节。

### 5. 验证（Stage 1，门全开）

- **合成毛刺语料**（`scripts/blip_gate_replay.py --synth --check`）：
  **CHECK PASSED**。12 组毛刺（RMS∈{0.005,0.01,0.02} × 时长{160–640}ms）
  零幻影 turn（毛刺块被门控或被模型直接判 idle，两种都算过——断言的是
  结果不是机制）；对照组（0.5× 增益弱第二句）照常 commit；整句文件
  （10s + 2s 尾静音）三句在 3.2 / 6.88 / 9.28s commit——**与基线时间点
  完全一致**，尾词「但是呢」也因尾静音落地（直播流同理），内容覆盖
  断言全过。
- **blip_turn_test**：3 pass / 0 fail（正常短句发话后 3.5s 触发话轮）。
- **真实麦克风录音回放**（40.96s 实录，最终配置）：44 个 nonidle、
  7 次 commit，文本与录音内容一致；pre-latch 块 RMS 最低 0.012——
  真人能量全部在门限之上，无一误伤。
- **可观测性**：被门控的块在 turn.log 打 `[TurnTaking] GATE session
  <8位> {…}`（gate 名 + 触发路径），每个未 latch nonidle 块附 p/rms
  诊断值（`diag`），上线后呼吸手势可直接在日志里对账。

### 6. 已知边界与代价

- **安静长句 commit 变慢 ~0.5–1.5s**：基线里 mistake 仲裁在句中提前
  拆句（「…我儿。」截断），现在整句走 wait 路径自然收尾（「…我儿子。」
  完整）。这是修复而非代价——正是补遗三 §4 的「句中拆句」问题。
- **残余风险**：能量足够大、且 paraformer 对其幻觉出非空文本的呼吸，
  三条件放行 + E 不拦（有文本）。只能靠 GATE/diag 日志观测到后再议
  （A 的概率门对这类块无效——模型自信地错）。
- **回滚**：五个开关（`nonidle_prob_gate` / `nonidle_rms_gate` /
  `mistake_no_text_reset` / `commit_no_text_reset` / `asr_seed_trim`）
  全部归零/false + 重启即恢复原行为。

### 1. 现场还原（会话 4870f7a3，23:00:25）

### 3. 修复：文本不再作为 latch 证据

真人 onset 的能量实测从未低于 RMS 门（合成语料 8 次 onset 最低 0.019，

### 4. 遗留边界

paraformer 的幻觉文本仍会在 idle 块上进入 cascade 流（partial 可能
闪现无意义字），但无 latch 即无 commit、无 LLM 污染——与「刚才」同类，
只影响 UI 瞬时显示。若后续仍观察到漏网（能量 ≥0.01 且带幻觉文本的

其与真人弱 onset 无分离度，不预先上。

## 补遗六：「从一数到十，数慢一点」——话轮边界切进词里（2026-11-05）

补遗五上线后的用户实测（会话 75d43f7b，11-04 23:34）：查完北京天气后说

### 1. 现场还原（mic 旁路录音逐 160ms RMS）

用户真实语音流：`好的好的` (09.3–10.9) → 0.64s 停顿 → `重新说，从一
数到十，` (11.7–13.0) → **无停顿**直接 `数慢一点` (13.1–13.6)。

1. **wait 路径 onset 竞态**：第 5 个 idle 块（11.705–11.865，RMS
   0.0388——正是「重」的 onset）被模型误判 idle，恰好凑满
   `max_wait_num=5` → wait commit + reset，把 onset 切在词中间。wait
   计数只看模型分类不看能量：呼吸（0.004）和真语音 onset（≥0.012）
   在能量上完全可分（补遗四标定），但 wait 路径没用它。
2. **complete 误判切在「十|数」中间**：13.0–13.14 块 RMS 0.086（「数」

3. **孤段谐音**：「数」onset 被 #2 吃掉，孤段「慢一点」无左上下文 →
   谐音「煮/走」。

LLM 侧其实已被 grace 窗 + groupby 兜住（回复同时回应数数与后续），
**用户可见问题 = UI 拆条 + ASR 文本损伤**，根源都是"边界切在词中间"。

### 2. 重放取证（Phase 1）

全 66s mic 经 `blip_gate_replay.py` 直连 ：8000 重放：wait 竞态**稳定
复现**（commit #1 恰在 t=24.48）；#2/#3 合并为单 complete 且文本正确

| # | 机制 | 位置 | 作用 |

| C | **wait 计数 RMS 否决** | `model.py` wait 路径 | idle 分类块计入 `wait_idle_cnt` 须同时 RMS < `nonidle_rms_gate`(0.01)。onset 块不再凑数；呼吸照常计数。复用 latch 标定不新调参。代价：话尾衰减块不再计数，真实 EOT 的 wait commit 晚 ~160–320ms |

`asr_seed_backoff_s: 0.0`。

**明确否决**：调大 `max_wait_num`（C 已根治竞态，全局加延迟得不偿失）；

  （「你数到哪了？」）。「说」是 **数（shǔ）→ 说（shuō）的同音瞬听**，
  在第三个 partial 就被自我修正。
- **「你是/你在这」**（01:56:02.78–02.98）：「你再查一下那个。」commit
  （02.109）后，下一句「呃，你再查一下那个湖人队」起始，partial 流
  `你是 → 你在这 → 你再查一 → 你再查一下…`，commit 05.338 干净。
  「是/在这」是 **再查（zài chá）→ 在/是/在这 的同音瞬听**。

mic 旁路录音逐 160ms RMS 证实：两处 partial 全部骑在**真人语音中段**
（RMS 0.05–0.13），不是呼吸、不是回声——与补遗三「刚才」骑呼吸的机
制同族但载体不同。同族闪现还有：「你在唱」（59.9，「再查」的另一种
瞬听）、「我迎/欢迎」（58.4–58.6）、01:57:45 的「你是」（紧跟助手自
己说出的「嗯？你是想说什么呀？」，属回声瞬听）。**所有这些词只出现
在 partial 流：无一进入任何 commit 或 LLM**——turn server 的五道门
（补遗四/五/六）保证幻觉不落地，但 partial 是逐块直发的显示流，门
管不到它。

### 2. 定性与修复选型

这是流式 ASR 的固有行为：识别器在只听到前 1–2 个音节时输出"最可能
的续词"，听到更多音频后自我修正。**用户可见问题 = 错误续词在 live
气泡里闪现 200–400ms**，纯显示层。可选修法：

- 换 cascade ASR 模型：治本但动整个标定体系（前次已否决，同补遗六）。
- 最小字数门（不显示 <3 字 partial）：「你说」「你是」是 2 字可挡，
  但「你在这」「你在唱」「今天的」3 字挡不住。
- **前缀确认制稳定性门（采纳）**：一个 partial 只有被**下一个
  partial 证实为前缀**（正常增长）才上屏；修正（非前缀）不上屏，只
  替换内部候选。零识别管线改动，纯 `frontend/script.js` 显示层。

### 3. 实现：`handleUserTranscription` 稳定性门

新增模块级状态 `stablePartial`（已被后续 partial 证实的前缀，当前上
屏文本）/ `pendingPartial`（最新候选）。partial 到达时：若
`pendingPartial` 是新文本的前缀且更长 → `stablePartial = pendingPartial`
（证实上屏）；否则视为修正，仅更新候选。上屏文本滞后一个 partial
更新（~160–320ms）。`final` / `append` / `selftalk_drop` 三处重置状态。
附带收益：**单次幻影 partial（「刚才」族）不再开气泡**——它等不到证实
就被 drop，气泡根本不创建。同时加了"显示文本未变则跳过重写与脉冲"守
卫，避免连续 partial 映射同一文本时气泡频闪。`index.html` script.js
版本号提至 `v=20261105a`（静态文件磁盘直出，浏览器刷新即生效，无需
重启服务）。

### 4. 验证：全会话 197 条 partial 回放

把 f083ab27 全会话 `ASR partial:` 流按时间序过一遍同逻辑门，对比上屏
序列与实际 commit：

- 「你说」「你是」「你在这」「你在唱」「我迎/欢迎」**全部不再上屏**
  （case1 上屏序列 `你 → 你 → 你数到哪`，case2 直到 `你再查一` 才首
  次上屏）；
- 唯一显示的「今天的」（05.642）经查是下一句「今天的比赛怎么样」的
  **真实句首**并被后续 partial 稳定证实——门的判定正确；
- 正常增长句的 live caption 仅慢一个更新（如「北京今天的天气怎么
  样」序列完整保留）；30 个 commit 文本全部原样上屏，无一受影响。

### 5. 边界

- 显示滞后一个 partial（~160–320ms）：首词上屏略慢，commit 文本不受
  影响（final 永远原样渲染）。
- 极短句（partial 只有一拍就 commit，如「呃，那个。」）live 气泡可能
  整句不显示、直接出现 final 文本——对超短句反而是更稳的行为。
- ASR 中途修正被隐藏直到重新证实：用户看到的 live caption 永远是
  "已证实前缀"，不会再看到任何被撤回的词。

## 补遗八：「也不是星期天的天气」——自说自话过滤吞掉真人纠错（2026-11-05）

用户报告：连续纠错被吞（「也不是星期天的天气。」「就查今天的。」「查今天
的北京天气。」）。取证结论：**turn server 五道门全部正常 commit 了这些话
轮，是 app 侧层 3 自说自话文本过滤把它们当回声丢弃了**——被吞句一个都没
进 LLM。

### 1. 现场还原（session 9e727c1f，10:24–10:27）

| 时刻 | 事件 |
|---|---|
| 10:24:14 | 用户：「嗯，你好你好，那个星期天的天气怎么样？」 |

drop 全部是同一句请求的变体。查天气最终也没查对。

### 2. 取证：被吞句的匹配源全是陈旧文本

把每条 drop 的文本对当时全部匹配源（12 个 assistant_chunks + pending +
最近 6 条历史）手算召回：

- 「就查今天的」（5 字）对 **40 秒前**的「让我查一下星期天的天气」：
  查/天/的 3 个 size-1 散块，recall 3/5 = 0.6，恰好过线；
- 「查今天的北京天气」对同一陈旧源：查+天+的+天气，6/8 = 0.75；
- 「你听到了吗」对几分钟前的历史消息；
- 而当时**正在播放**的道歉句对这些句子的召回只有 0.4–0.5，反而不构成
  匹配——罪魁不是在播音频，是 40–60 秒前的旧文本。

回声物理：麦克风只能拾取**正在播放或刚结束数秒**的音频，永远拾取不到
40 秒前的声音。旧逻辑的源跨度却是分钟级（12 chunk 无时间戳滚动 +
pending + 最近 6 条历史）。纠错话轮的定义恰恰是引用助手刚说过的词再否
定它——短句引用话题词（「星期天的天气」6/9 = 0.67）在召回意义下与回声
不可分，唯一可靠的判别量是**源的新鲜度**。

反向审计全部 18 条历史 drop：12 条是本事故；11-05 01:24「嗯，你帮我。」
是用户查天气请求被 turn server 拆出的前导碎片（在播句已结束 5s）；两次
「嗯，好的好的。」同理；3 条「您太紧张了我儿。」是用户称呼（"我儿"）
混入助手词（"您…紧张"），且距在播音频 12s+。**日志留存期内零真回声
drop——该过滤器至今纯误杀。**（真回声防御仍需保留：扬声器场景回来时
它是唯一防线，见 §3。）

### 3. 修复：回声物理窗口 + 形态学两门（pvad_gate.py / app.py）

**源裁剪（主修）**——`_pvad_selftalk_text` 只把"物理上可能正到达麦克
风"的 chunk 当匹配源：

- 当前播放 run：按播放头估计 `pos = min(now − first_emit, total)`
  （复用圆环状态门已有的实时播放模型；`min()` 让 pos 在 chunk 间生成
  间隙自动冻结），只取 `cum_end ≥ pos − 4s` 的 chunk——长 run 里早已
  播完的早期 chunk 不再是源；
- 旧 run：只保留被打断后 ~5.5s（grace+tail）内的条目；
- **history 与 pending 永不做源**：一切播过的话都经 `_speak_chunk` 进
  了 assistant_chunks，二者纯冗余且时间上不可能；
- 无播放且无刚打断 → 直接放行（回声物理不可能）。

记账改造：`assistant_chunks` 由纯文本改为 `{text, run, cum, ts}`，
`_speak_chunk` 在 run 首个音频落地时 bump `playback_run_serial` 并记录
首播时刻/累计秒数。随 get_history 钩子退役删除。

**形态学两门（辅修，救播放中话题重叠）**——时间窗救不了"对正在播的内
容纠错"（「查今天的北京天气」对在播「我现在马上去查一下北京最新的天气
情况」召回 0.625），补两条形态判据：

- **跨度效率门**（全长度）：回声是播放音频中**一段连续语音**的转写，
  匹配块在源文本里也紧挨（缝隙只容被糊掉的字符）；纠错把用户自己的词
  插在引用的话题词之间——「查**今天的**北京天气」vs「查**一下**北京
  **最新的**天气情况」5 字匹配跨 10 字源跨度（效率 0.5）。效率 < 0.6
  判用户；
- **短句连续门**（len<8）：最大匹配块须 ≥ len−2——「就查今天的」的
  3 个 size-1 散块是用户；「怎么又喊我婉儿呀」最大块 5/8（中部一个糊
  字）是回声。

## 补遗九：「嗯，然后你从。」——wait 提交的结构真相与 token 可观测性（2026-11-05）

### 1. 事故

用户说「嗯，然后你从」（在组织"从一数到二十"的数字范围）时句中停顿
1.1 s（mic RMS 落到噪底 0.0005，真静音），wait 路径于 12:06:33.79 提
交了碎片话轮；用户 33.86 续说，几乎与提交同时。填充回复「嗯，你好像
想说从哪查起呢？」刚起播即被 barge-in 掐掉（Ratio 0.27）。最终回复因
LLM 侧 groupby 合并话轮而内容正确，属可调参数问题而非功能缺陷。

### 2. 结构真相（修正一个此前报告中的错误认知）

此前我们描述 wait 路径为"不懂语义的静音计时器"。**这不准确**：

- `monitoring_wait_silence` 只能由 `<|user_incomplete|>` 武装
  （`model.py` 话轮分支；有真实文本时 `mistake_no_text` 降级路径不
  适用，是唯一入口）；
- 因此本次的 token 序列是：`nonidle…nonidle` → **`incomplete`（模型
  判对了"没说完"）** → `idle`×5 → wait commit。不是"话轮判定说完了"，
  而是"模型判定没说完、但静音持续 `turn_wait_ms`（800 ms）后系统决
  定不再等"；
- 纯语义 complete 路径（argmax 直接出 `<|user_complete|>` → 秒提交）
  本次未触发——否则 900 ms 宽限窗会接住 33.86 的续话并留下
  premature drop 日志（实际无此行）；
- "思考停顿 vs 说一半放弃"这个歧义由 `turn_wait_ms` 滑线消解（UI 可
  调 160–3200 ms），不是 bug。

### 3. 可观测性根修

**取证缺口**：逐块 state 行（"User hasn't finished speaking, wait" 等）
全部在 `developer_mode` 后面（`config.yaml: developer_mode: false`），
commit 不落任何日志，app 的 ASR result 行不带触发路径——本次结论只能
靠 mic PCM + 时间差反推。改法（repo 仓 `<本次提交>`）：

- **`service/model.py`**：`process()` 新增两个逐块瞬态——`state_log`
  （分派状态 token 变化时 `{from, to}`，短名 `idle/nonidle/incomplete/
  complete/backchannel/assistant_*`，reset 后首块记 `start`；prev 取自
  `past_state["state"]`，本就随 snapshot/restore_runtime 按会话承载，
  共享模型跨会话安全）与 `commit`（`{trigger, text}`，wait/complete
  两个提交点各一处）；
- **`server.py`**：STATE/TURN 常开行，与 GATE 行同通道同 flush 纪律——
  `STATE session <8位> nonidle -> incomplete`、`TURN session <8位>
  commit trigger=wait text=…`。状态**变化才打**，不逐块刷屏；
- **`dialogue_system/app.py`**：`ASR result` 行加触发路径标注
  `ASR result (complete|wait turn): …`（web.log 有时间戳，可与其余事
  件对齐）；sessions API 的日志解析正则改为可选捕获组，**旧格式行照
  常解析**（trigger 为空），新行事件带 `trigger` 字段；
- **`frontend/index.html`**：两个滑条更名并写明 token 语义——
  "Incomplete→wait silence"（`<|user_incomplete|>` 后须静音多久才提交）
  与 "Complete grace window"（`<|user_complete|>` 的宽限窗）。两者
  2026-10-30 起本就前端可调、热推送 turn server，本次只是让名字对上
  语义。

### 4. 验证
