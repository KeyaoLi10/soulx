# 内网访问与浏览器安全上下文 — 麦克风/Audio Engine 报错原理解析

**日期**:2026-10-26
**背景**:同事经公司内网访问 Web 对话服务时,页面能打开,但报
"Audio Engine initialization failed! Only supported in localhost or https",
且麦克风不可用;tailscale(https)访问则一切正常。本文记录原因、原理与
最终采用的解决方案,供以后同类问题直接参考。

---

## 1. 现象与结论速览

| 访问地址 | 页面 | 麦克风 | TTS 引擎(SAB) |
|---|---|---|---|
| `https://…tail0ea2ce.ts.net:8443`(tailscale) | ✅ | ✅ | ✅ |
| `http://172.31.48.7:8090`(公司内网,明文 http) | ✅ | ❌ | ❌ 弹窗报错 |

**一句话结论**:这是浏览器安全策略,不是服务故障。浏览器判定
"明文 http + 非 localhost" 的源为**非安全上下文(non-secure context)**,
直接不注入麦克风和 SharedArrayBuffer 两类 API。**服务端任何配置都
无法绕过,唯一出路是让访问地址变成 https(或 localhost)或让浏览器
把该 http 源当作安全源。**

## 2. 原理

### 2.1 什么是 Secure Context(安全上下文)

浏览器把页面按来源(origin)分为两类:

- **安全上下文**:`https://` 任意主机,或 `http://localhost` / `http://127.0.0.1`;
- **非安全上下文**:其余所有明文 `http://`(例如 `http://172.31.48.7:8090`)。

理由:明文 http 链路上任何中间人都可以篡改页面、注入脚本。如果这类
链路能调用麦克风、摄像头、共享内存等高权限 API,等于把窃听器和进程
内存暴露给链路上的攻击者。因此 W3C 规定**高权限 API 只在安全上下文
暴露**,在非安全上下文里连对象都不存在(`undefined`),不是"调用报错"。

### 2.2 本服务踩中的两个 API

前端(`frontend/script.js`)的两处依赖都属于此类:

1. **`navigator.mediaDevices.getUserMedia`(麦克风)**——采集用户语音的
   唯一入口。非安全上下文下 `navigator.mediaDevices` 为 `undefined`。
2. **`SharedArrayBuffer`(TTS 播放环形缓冲)**——`initTTSAudioEngine()`
   里 `new SharedArrayBuffer(8 + 24000*120*4)` 与 AudioWorklet 通过共享
   内存传音频。非安全上下文下 `SharedArrayBuffer` 为 `undefined` →
   `new` 抛 `TypeError` → catch 弹出
   "Audio Engine initialization failed! Only supported in localhost or https"。
   报错文案里的 "localhost or https" 指的就是安全上下文判定条件。

注意顺序:先弹这个窗的是 TTS 引擎初始化,但即使没有这行报错,麦克风
那关也过不去——两者是同一根因的两个症状。

### 2.3 为什么 COOP/COEP 响应头救不了

`app.py` 的中间件给每个响应加了:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

这一对头的作用是开启 **cross-origin isolation**(让 `crossOriginIsolated
=== true`,是 `SharedArrayBuffer` 在**安全上下文内**可用的附加条件)。
但它**不参与**安全上下文判定——明文 http 的源无论加什么头都是非安全
上下文。tailscale 路径正常,正是因为它先满足了 https 这个大前提。

### 2.4 为什么 tailscale 路径正常

tailscale 暴露的是 `https://frc-eot-demo.tail0ea2ce.ts.net:8443`,
带由 Tailscale 签发的有效证书 → 安全上下文 → 全部 API 可用。

## 3. 解决方案对比(2026-10-26 实测)

| 方案 | 做法 | 结论 |
|---|---|---|
| ① 自建 TLS 反代(8444) | `services/https_proxy.py`,自签证书反代 8090 | **已部署又撤下**:服务器本机验证全通(页面/静态资源/wss 全链路 ASR 正常),但用户内网机器到 8444 端口不通——内网到服务器之间大概率有端口级 ACL(8090 放行、8444 未放行),非服务问题 |
| ② 改 root caddy(8443) | `/etc/caddy/Caddyfile` 加 `tls internal` 站点 | 未实施(需 sudo)。注意:内网直连 `https://172.31.48.7:8443` 目前命中的是 root caddy 默认站点——**旧的 frc_eot_demo**(:9800),不是本服务,别用该地址 |
| ③ **浏览器 flag(已采用)** | 见下节 | ✅ 当前在用,即刻生效,无需动服务器 |

## 4. 最终方案:Chrome 安全源 flag 设置方法

让浏览器把指定的 http 源**当作安全上下文**(仅对本机浏览器生效):

1. Chrome 地址栏输入:`chrome://flags/#unsafely-treat-insecure-origin-as-secure`
2. 文本框填:`http://172.31.48.7:8090`(必须带 `http://` 前缀,只填这一个源)
3. 右侧下拉选 **Enabled**
4. 点底部 **Relaunch** 重启浏览器
5. 重新打开 `http://172.31.48.7:8090`,麦克风与 Audio Engine 正常
   (地址栏"不安全"字样可能仍在,不影响功能)

**局限**:按机器生效,换电脑要重设;Chrome 大版本升级可能重置 flag;
不适合大规模分发给非技术同事(每台都要手工设置)。

## 5. 经验沉淀

1. **"页面能打开"不代表"功能能用"**:非安全上下文下页面、JS、CSS、
   WebSocket 全部正常,只有高权限 API 缺失。遇到"麦克风不可用 /
   SharedArrayBuffer 报错",先看地址栏是不是明文 http + 非 localhost。
2. **判断口诀**:Secure Context = `https` 任意主机,或 `http://localhost`。
   服务端设置(COOP/COEP 等)只能锦上添花,不能无中生有。
3. **排查此类问题的顺序**:地址栏协议 → `window.isSecureContext`(控制台
   一行即知)→ 再查服务端。本次在控制台执行 `window.isSecureContext`
   即可立刻确认。
4. **内网端口连通性**:服务器本机 curl 通 ≠ 内网可达,中间可能有端口级
   ACL;新增端口前先让同事 `curl -k https://<ip>:<port>` 验证连通再部署。
5. 遗留资产:`services/https_proxy.py` 与 `services/certs/` 保留未删,
   若日后内网放行 8444 或想换端口,一条命令即可重启:
   `tmux new-window -t soulx -n intranet 'venv/bin/python services/https_proxy.py 2>&1 | tee -a logs/https_proxy.log'`
