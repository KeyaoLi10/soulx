§0一句话与分层总览

一个 0.6B 流式语义轮次预测模型（SoulX-Duplug）挂在 Qwen3.5-9B 快慢脑双实例 + VoxCPM2 流式 TTS 级联前端上， 外加 pre-ASR 主说话人迟滞门控（pvad 流门控 + 影子声源分离）、五层话轮边界防御， 以及 Agent Runtime 控制平面（快脑语义路由 + 五道守卫 · 双路并行：闲聊路口播 / 路由路任务 · SQLite 持久化任务协议 · run 围栏调度 · 三态交付 + 单一出口 + 重播重入）， 构成全双工中文语音对话系统。

层组件职责

§1全局架构图（数据流 + 控制流）

下图是整个系统的一次完整环流：上行（琥珀色）从麦克风经 WebRTC 处理、WS 二进制帧进入 web app 接收循环， 旁路喂 pvad 打分 / tse 影子分离，过流门控后进 turn server 状态机；轮次提交（绿色）携带整句转写回到话轮管线； 生成（蓝色）在闲聊/表达脑流式分段，经统一语音出口送 TTS 合成、下行回浏览器； Agent Runtime 控制面（紫色）承接每一句话轮时同开两路：闲聊路过 grace 门即生成口播（本轮应承 / 寒暄 / 反问）， 路由路在后台出任务计划 → 操作落库 → 回执仲裁 → 慢脑执行；结果播报只走交付泵单一出口，全部复用同一条语音出口。

1.1 一次对话的端到端时序（文字版）

  1. 上行：麦克风 → 浏览器 WebRTC 链 → WS 二进制帧（16 kHz float32，160 ms）→ web app 接收循环（异采样率 soxr VHQ 重采样）。
  2. 旁路与门控：原始 chunk 先进 pvad ring（1.2 s 尾窗）与 sidecar feed（打分器必须看到真实麦克风，否则门永远无法解除）， 再过 stream_gate_filter——主动门控 + 已注册 + 压制生效时把 chunk 替换为全零块；tse :8087 仅影子观测 sep_cos。
  3. 轮次判别：chunk 进 turn server 状态机（0.6B 逐 chunk），五道门滤掉毛刺；wait（连续静音 max_wait_num 块）或 complete（<|user_complete|> 即触发）提交话轮，携带整句转写 + trigger + commit_id。
  4. 两遍式 ASR：turn server commit 后立刻整句重识别并异步推 turn_final；话轮管线在后台线程 hold ≤500 ms 等它，拿到更准的整句文本再继续（超时回落 live 文本）。
  5. 管线：自说自话过滤 → 主说话人门 → 提交上一轮 pending → interrupt/reset（慢脑播报中不满足持续插话阈值 → hold 让路，见 §4）→ 历史 → Agent Runtime 接管（详见 §4–§8）。
  6. 双路并行：接管后同开两路——闲聊路过 grace 门即流式生成上口（本轮应承 / 寒暄 / 反问归它，首句 ~1 s）；路由路在后台出任务计划（§5）。
  7. 生成与播放：闲聊/表达脑流式分段 → 统一语音出口：宽限保持（complete 触发时）→ text_response → TTS 流式 → audio_chunk 下行 + 双轨录音；播完挂 pending_message，下一轮话轮提交时才写进历史。
  8. 打断：播放期用户复语 → pvad barge-in（间隙容忍累积证据）→ cut_pending_audio + interrupt → 三态返回；慢脑结果播报有独立加强阈值（§4）。
  9. 后台交付：慢脑结果落 outbox → 交付泵等空闲（≥1.2 s 静音 ∧ 无生成 ∧ 无播放）经同一出口播出——闲聊路从信息层面拿不到结果原文（单一出口，§9）。

§2上行链路：麦克风 → 轮次提交

上行链路的设计原则：门控在 ASR 之前（非主说话人音频根本不进转写与轮次判别），打分在门控之旁 （打分器必须持续看到原始麦克风，否则压制永远无法解除），修正在线程之内（两遍式 ASR 的 hold 发生在话轮 后台线程，绝不阻塞事件循环）。

2.1 pvad 流门控：迟滞状态机

两个说话人的 ECAPA 余弦分数带完全重叠（用户 −0.06–0.39 vs 背景 0.11–0.40），任何单一阈值都不可行， 因此用迟滞 + 死区：进入压制要求连续 2 轮显著低于阈值，解除只要求一轮回到阈值之上。

§3话轮边界五层防御级联

一次"用户复语 / 背景噪声 / 回声"事件要成为一次合法话轮，必须依次漏过五层防御。 每层只杀一类目标，层与层不合并阈值（mm=3 与 D=5 不可合并是实测结论）。

§4话轮管线与统一语音出口（生成 → 播放）

话轮管线是"说完之后怎么办"的唯一实现。它先过一遍收尾防御（自说自话 / 主说话人门）， 随后把话轮连同 gen_sn（收音循环 commit 时置位的生成标志序号）一起移交 Agent Runtime； 所有输出——回执、澄清、表达轮、后台结果交付——汇入统一语音出口：同一条 _run_speech_pipeline、 一个 turn_start、一个 pending-message 生命周期、一套三态返回。

4.1 双轨录音与打断取证

TTS 发射快于实时（RTF ≈0.36），浏览器在打断瞬间丢弃缓冲，但旁路可能已持有"已发射未播放"的尾巴。 _SessionAudio 以播放时钟（首发射时间）为 run 锚点：每次管线启动 run_break(first_emit_time) 声明断流（迟到的 mark_cut 永远切不到新管线的 run）；打断路径 cut_pending_audio → mark_cut(t, since) 把录音切在可听播放真正结束处。pvad barge-in、话轮提交、交付入口、duplex_stop、连接关闭六个入口都先切刀再 interrupt。

§5双路并行：闲聊路与路由路的仲裁

接管每一句话轮后，Agent Runtime 同开两路（2026-11-06 双路并行改造，全部提速与吞句根修的来源）： 路由脑出一份计划要 3.5–4.3 s（attempts=2 翻倍），用户等不起——所以闲聊路（voice lane）过 grace 门就开始 /chat 流式生成并上口，负责本轮全部常规口播（应承「我去查」/ 寒暄 / 没说清时反问 / 任务情况按面板答）； 路由路（agent lane）只在后台做任务机器。两路共用同一个 grace 门阈值、同一个任务面板快照， 仲裁规则保证它们永不双声道。

闲聊路 voice lane路由路 agent lane
驱动闲聊路线程（chitchat_fn → :6007 /chat，TEMP 0.9）话轮线程（submit_request → :6009 /agent_chat_v2，greedy 0）
开口时机grace 门开后首句 ~1 s 流式进 TTS不直接开口——回执按仲裁规则上口或静音
职责本轮口播：应承 / 寒暄 / 反问 / 按面板答任务情况计划：create / amend / cancel / get_task … → 落库 → 慢脑
信息面拿不到结果原文——只见状态摘要 + 用户实际听到部分（渐进式披露）全量：快照 + 慢脑结果 + 交付记录（SQLite）
失败chitchat_failed → 全套回退旧路径（回执照播 / clarify 上口 / 表达轮）传输故障 → 终态；被取代 → route_stop 断流（取消不是失败）

两个容易踩坑的细节（均实测事故根修）：吸收轮也必须释放 gen 标志——纯应答「嗯，好的」被吸收后直接 return， commit 时置位的 gen_in_progress 无人清理，后台交付被永久拒绝（T2 完成后 14.5 s 无声），且 _reply_in_flight 恒真 让 blip 过滤在完全静止期吞掉真实短句；长间隔独立话轮绝不杀在途路由——route_stop 只能作废"还没返回的路由"， land_pending 只能救"已返回挂起的计划"，先杀后判窗口会两头落空（C罗查询 11 s 永远 registered，用户每次追问都精确杀掉在途路由）。

§6Agent Runtime：控制平面全景

Agent Runtime 是系统的任务编排层，回答四个问题：用户说了什么（路由器 + 五道守卫）、 系统承诺了什么（操作落库 + 受控回执）、承诺执行得怎么样（慢脑 run 围栏 + 事件信封）、 结果什么时候说、怎么说（交付管理器 + 统一语音出口三态，闲聊路拿不到结果原文）。 分工原则一以贯之：确定性逻辑放 Runtime（守卫、回执模板、状态机、lease 围栏、重播重入、双路仲裁）， 概率性逻辑放模型（路由 LLM、闲聊路与表达轮生成、慢脑工具循环）——SQLite 是两者之间唯一的交接面。

对语音前端的接入是只读注入：grace 阈值取同一份 turn_grace_ms（不另起计时器）、 话权判断取现有 _agent_can_deliver、发声复用同一条 _run_speech_pipeline—— 不复制任何语音逻辑，也就不会出现第二套"怎么说"的行为。

§8路由器与五道守卫 + 回执话术模板

路由器（agent/router.py）是控制平面唯一的决策入口。每次话轮，它把 系统提示 + 8 条 few-shot + 截断历史 + 快照渲染发给路由脑 :6009，要求以一次 route_turn 工具调用返回 plan_json（few-shot 从 16 对砍到 8 对是路由提速三件套之一： prompt 3.5k → 1.8k token，被砍 8 例的语义全在系统提示硬规则里）。主循环是 for i in range(1 + repair_attempts)（修复轮 ≤1）：每轮先取计划 （优先读 route_turn 工具调用参数，文本中的裸 JSON 只作兜底），再依次过五道守卫； 守卫不过就把纠错提示追加为 user 消息重跑一轮（修复原因上日志 [router] repair 1/1 after: …）。 传输层失败（HTTP 错误、流截断、finish_reason≠stop）没有修复资格——直接终态，不上任务，上口固定澄清话术。

五道守卫顺序固定，全部是纯字符串运算，不增加任何模型调用；第 ②③④⑤ 道各自来自一起实机事故：

  1. 格式守卫 parse_plan：schema_version、reply_mode 白名单、操作白名单、 各字段长度上限、local_ref 唯一性与依赖存在性、clarify 必须带 clarification。 任何不合法丢弃整批——结构不合法绝不能执行。
  2. 接地守卫 _ungrounded_quote：每个操作的引用（quote）归一化 （_NORM_RE 去空白与中英文标点）后，必须是本轮用户原文的子串—— 模型不能引用用户没说过的话。evidence 三种写法都收：顶层 quote、 evidence_quote、嵌套 evidence.quote。指称对象只在上一轮说过 （本轮只是附和 / 催促）时，操作照出但 quote 留空——留空不声明锚定，放行。
  3. 吞句守卫 _stop_only_leftover：整批只有 stop_speech 时，归一化后引用之外的 原文超过 16 字即判吞句——「等一下等一下……顺便查一下湖人比赛」被吞成 21 秒安静的 事故由此而来（事故句剩 30 字，正常填充词不到 10 字）。
  4. 取消目标守卫 _cancel_targets_ungrounded：取消的破坏力最大（杀运行任务 + 毒化已完成任务的播报）。目标"被引用" = label 二元字组命中归一化原文，或整句是纯取消话 （含取消词且去掉取消词 / 指示词 / 语气词后无剩余，如「算了」「那个先取消」）； 都不满足 → 修复轮 _CANCEL_NOTE → 仍败终态拒绝。scope=all_active 只要求原文含取消词。
  5. get_task 目标守卫 _get_task_target_ungrounded：泛泛追问（「查了吗」「怎么样了」） 不该指向已完整播报的旧任务。同时满足——label 不命中 ∧ 任务已了结且已播报 / 已取消播报 ∧ 本轮无重播意图（_REPLAY_RE「再讲一遍」类）→ 修复轮 _GET_NOTE → 仍败终态拒绝； running / 未播出的目标放行（泛泛追问的天然落点）。

§8.2 受控回执话术模板（receipt_text）

回执话术由程序模板生成，不让模型自由解释"操作是否发生"：〈名〉来自经过校验的任务 label（缺省回退 task_id），模板外的内容不进 TTS。适配层逐条顺序上口，打断即终态， 本轮剩余回执不再上口。闲聊路活着时，受理 / 状态类回执整批静音（§5 仲裁）—— 下表在实际话路上只剩纠错 / 失败类会播出。

§9任务与交付生命周期：单一出口 · 三态证据 · 重播重入

调度与交付分离：慢脑只负责把任务跑到终态（completed / failed / waiting_input）， 结果何时、如何到达用户耳朵是交付泵（agent/delivery.py）的职责。 泵每次开口走 speak_fn(envelope, text, stop_event)，返回值三态与语音前端 _run_speech_pipeline 的约定逐条对齐（语音前端本身不动）： True 完整播出 → sent_unconfirmed → played_confirmed（发射侧估计）； False 播出后被打断 → interrupted_partial，终态，不自动重播； None 一个字没播 → 静默重试 ≤3，耗尽 → retry_exhausted（不写 delivered，结果仍可查询）。 不可送达（话权被占）时有界等待 2 s 后归还 outbox，不硬抢话轮。

单一出口（2026-11-07 根修）：结果播报的唯一出口是交付泵。闲聊路上下文不注入 结果原文（§8.1 渐进式披露），闲聊路无文本可复述——机制从根上消灭"闲聊路说一遍、 泵又播一遍"的复读；用户说"再讲一遍"只能由泵兑现（重排 deliver），闲聊路不代劳。 唯一例外是窄版 voiced_by_lane（2026-11-09）：「讲个笑话」被建成任务后，慢脑 零工具自产另一个笑话，结果在面板挂"待播报"1 分 54 秒（泵让路），闲聊路只能当场 和稀泥。根修：创建轮闲聊路亲口说过（creation_voiced 事件）∧ 完成的 run 零工具调用 ∧ 该任务首个 run，三条件同时成立 → 结果视同已播报，泵不入队。 零工具是判别器——天气 / 体育类查询必带工具，照常走泵；首 run 条件防 rerun / amend （第二次执行必带上下文）被误杀。

重播重入（2026-11-09 收紧）：get_task 显式追问时分两种语义—— _request_wants_replay 查本轮原文是否含重播词（「再讲一遍 / 重新 / 一遍」类）： 纯状态问句（「查了吗」「怎么样了」）对已完整播出的结果不重播，回执 already_delivered「结果刚才也说过啦，想再听就说一声」；带重播词才 _reopen_delivery 重开重排（重开白名单 7 态：interrupted×2 / retry_exhausted / suppressed / sent_unconfirmed / played_confirmed / voiced_by_lane）。用户没听过的结果 （打断 / 重试耗尽）无需重播词照常重排——欠的账总要还。

取消抑制与掐音：cancel_tasks 落在已 completed 任务 → 置 cancel_intent=1， 两道 SpeechEnvelope 校验（valid_for 对 result 类）都拒绝 → 交付落 suppressed； 同时 stop_speaking_for_task / stop_speaking 跨线程置 stop_event 掐掉在途播报（泵线程被 speak_fn 占住，走队列 stop_speech 轮不到自己）； _cut_speech_for_cancels 在 commit / land 后扫回执，单目标掐该任务、 all_active 掐会话当前在播。面板渲染「结果已取消播报」（绝不吊人）；get_task 重播清回标记。
