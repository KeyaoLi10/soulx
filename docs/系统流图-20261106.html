§0一句话与分层总览

一个 0.6B 流式语义轮次预测模型（SoulX-Duplug）挂在 Qwen3.5-9B 快慢脑双实例 + VoxCPM2 流式 TTS 级联前端上， 外加 pre-ASR 主说话人迟滞门控（pvad 流门控 + 影子声源分离）、五层话轮边界防御， 以及 Agent Runtime 控制平面（快脑语义路由 + 三道守卫 · SQLite 持久化任务协议 · run 围栏调度 · 三态交付 + 重播重入）， 构成全双工中文语音对话系统。

层组件职责
接入层浏览器（WebRTC AEC/NS/AGC）回声消除与降噪；16 kHz mono、160 ms/chunk 上行 WS；24 kHz PCM 分块下行回放
门控层pvad 流门控（pvad_stream.py + :8086 sidecar）pre-ASR 迟滞门控：非主说话人音频（背景视频等）压制为全零块，不进 ASR / 转写 / 轮次判别
门控层tse 影子分离（:8087，可选）MossFormer2 分离 + 逐窗挑流，仅影子上报 sep_cos，不参与任何决策（负结果保留）
轮次层SoulX turn server :8000（GPU5）0.6B 状态机逐 chunk 判 idle/nonidle/speak；五道毛刺门；流式 paraformer 转写 + commit 后整句重识别（turn_final）
应用层Web app :8090（FastAPI + WS）会话管理、接收循环、话轮管线、宽限窗、能量守卫、回声防御、统一语音出口、双轨录音取证
Agent 层Agent Runtime（进程内，agent/）控制平面：快脑路由 + 三道守卫、受控回执模板、SQLite 持久化、run 围栏调度、三态交付 + 重播重入、任务面板 UI 泵
模型层快脑 :6007（GPU6）/ 慢脑 :6008（GPU1）同一 Qwen3.5-9B 双实例：路由与表达轮（/chat · /agent_chat_v2）/ 后台任务工具循环（make_v2_runner）
语音层VoxCPM2 :8085（GPU7）文本分句流式合成；自训 LoRA + 锚定音色 + 服务端文本正则化

§1全局架构图（数据流 + 控制流）

下图是整个系统的一次完整环流：上行（琥珀色）从麦克风经 WebRTC 处理、WS 二进制帧进入 web app 接收循环， 旁路喂 pvad 打分 / tse 影子分离，过流门控后进 turn server 状态机；轮次提交（绿色）携带整句转写回到话轮管线； 生成（蓝色）在快脑流式分段，经统一语音出口送 TTS 合成、下行回浏览器； Agent Runtime 控制面（紫色）承接每一句话轮：路由 → 操作落库 → 回执上口 → 慢脑执行 → 空闲交付，全部复用同一条语音出口。

1.1 一次对话的端到端时序（文字版）

  1. 上行：麦克风 → 浏览器 WebRTC 链 → WS 二进制帧（16 kHz float32，160 ms）→ web app 接收循环（异采样率 soxr VHQ 重采样）。
  2. 旁路与门控：原始 chunk 先进 pvad ring（1.2 s 尾窗）与 sidecar feed（打分器必须看到真实麦克风，否则门永远无法解除）， 再过 stream_gate_filter——主动门控 + 已注册 + 压制生效时把 chunk 替换为全零块；tse :8087 仅影子观测 sep_cos。
  3. 轮次判别：chunk 进 turn server 状态机（0.6B 逐 chunk），五道门滤掉毛刺；wait（连续静音 max_wait_num 块）或 complete（<|user_complete|> 即触发）提交话轮，携带整句转写 + trigger + commit_id。
  4. 两遍式 ASR：turn server commit 后立刻整句重识别并异步推 turn_final；话轮管线在后台线程 hold ≤500 ms 等它，拿到更准的整句文本再继续（超时回落 live 文本）。
  5. 管线：自说自话过滤 → 主说话人门 → 提交上一轮 pending → interrupt/reset → 历史 → Agent Runtime 接管（详见 §4–§7）。
  6. 生成与播放：快脑流式分段 → 统一语音出口：宽限保持（complete 触发时）→ text_response → TTS 流式 → audio_chunk 下行 + 双轨录音；播完挂 pending_message，下一轮话轮提交时才写进历史。
  7. 打断：播放期用户复语 → pvad barge-in（间隙容忍累积证据）→ cut_pending_audio + interrupt → 三态返回。

§2上行链路：麦克风 → 轮次提交

上行链路的设计原则：门控在 ASR 之前（非主说话人音频根本不进转写与轮次判别），打分在门控之旁 （打分器必须持续看到原始麦克风，否则压制永远无法解除），修正在线程之内（两遍式 ASR 的 hold 发生在话轮 后台线程，绝不阻塞事件循环）。

2.1 pvad 流门控：迟滞状态机

两个说话人的 ECAPA 余弦分数带完全重叠（用户 −0.06–0.39 vs 背景 0.11–0.40），任何单一阈值都不可行， 因此用迟滞 + 死区：进入压制要求连续 2 轮显著低于阈值，解除只要求一轮回到阈值之上。

§3话轮边界五层防御级联

一次"用户复语 / 背景噪声 / 回声"事件要成为一次合法话轮，必须依次漏过五层防御。 每层只杀一类目标，层与层不合并阈值（mm=3 与 D=5 不可合并是实测结论）。

§4话轮管线与统一语音出口（生成 → 播放）

话轮管线是"说完之后怎么办"的唯一实现。它先过一遍收尾防御（自说自话 / 主说话人门）， 随后把话轮连同 gen_sn（收音循环 commit 时置位的生成标志序号）一起移交 Agent Runtime； 所有输出——回执、澄清、表达轮、后台结果交付——汇入统一语音出口：同一条 _run_speech_pipeline、 一个 turn_start、一个 pending-message 生命周期、一套三态返回。

4.1 双轨录音与打断取证

TTS 发射快于实时（RTF ≈0.36），浏览器在打断瞬间丢弃缓冲，但旁路可能已持有"已发射未播放"的尾巴。 _SessionAudio 以播放时钟（首发射时间）为 run 锚点：每次管线启动 run_break(first_emit_time) 声明断流（迟到的 mark_cut 永远切不到新管线的 run）；打断路径 cut_pending_audio → mark_cut(t, since) 把录音切在可听播放真正结束处。pvad barge-in、话轮提交、交付入口、duplex_stop、连接关闭六个入口都先切刀再 interrupt。

§5Agent Runtime：控制平面全景

Agent Runtime 是系统的任务编排层，回答四个问题：用户说了什么（路由器 + 三道守卫）、 系统承诺了什么（操作落库 + 受控回执）、承诺执行得怎么样（慢脑 run 围栏 + 事件信封）、 结果什么时候说、怎么说（交付管理器 + 统一语音出口三态）。分工原则一以贯之： 确定性逻辑放 Runtime（守卫、回执模板、状态机、lease 围栏、重播重入），概率性逻辑放模型 （路由 LLM、表达轮生成、慢脑工具循环）——SQLite 是两者之间唯一的交接面。

对语音前端的接入是只读注入：grace 阈值取同一份 turn_grace_ms（不另起计时器）、 话权判断取现有 _agent_can_deliver、发声复用同一条 _run_speech_pipeline—— 不复制任何语音逻辑，也就不会出现第二套"怎么说"的行为。

§7路由器与三道守卫 + 回执话术模板

路由器（agent/router.py）是控制平面唯一的决策入口。每次话轮，它把 系统提示 + 16 条 few-shot + 截断历史 + 快照渲染发给快脑，要求以一次 route_turn 工具调用返回 plan_json。主循环是 for i in range(1 + repair_attempts)（修复轮 ≤1）：每轮先取计划 （优先读 route_turn 工具调用参数，文本中的裸 JSON 只作兜底），再依次过三道守卫； 守卫不过就把纠错提示追加为 user 消息重跑一轮。传输层失败（HTTP 错误、流截断、 finish_reason≠stop）没有修复资格——直接终态，不上任务，上口固定澄清话术。

三道守卫顺序固定，全部是纯字符串运算，不增加任何模型调用：

  1. 格式守卫 parse_plan：schema_version、reply_mode 白名单、操作白名单、 各字段长度上限、local_ref 唯一性与依赖存在性、clarify 必须带 clarification。 任何不合法丢弃整批——结构不合法绝不能执行。
  2. 接地守卫 _ungrounded_quote：每个操作的引用（quote）归一化 （_NORM_RE 去空白与中英文标点）后，必须是本轮用户原文的子串—— 模型不能引用用户没说过的话。evidence 三种写法都收：顶层 quote、 evidence_quote、嵌套 evidence.quote（few-shot 教的是嵌套形， 曾长期被解析器静默丢弃，导致接地守卫形同虚设）。
  3. 吞句守卫 _stop_only_leftover：整批只有 stop_speech 时，归一化后引用之外的 原文超过 16 字即判吞句——「等一下等一下……顺便查一下湖人比赛」被吞成 21 秒安静的 事故由此而来（事故句剩 30 字，正常填充词不到 10 字）。

§7.2 受控回执话术模板（receipt_text）

回执话术由程序模板生成，不让模型自由解释"操作是否发生"：〈名〉来自经过校验的任务 label（缺省回退 task_id），模板外的内容不进 TTS。适配层逐条顺序上口，打断即终态， 本轮剩余回执不再上口。

§8任务与交付生命周期（状态机 + 重播重入）

任务（做什么）与交付（什么时候说）是两条独立的状态机：任务停在 completed 不代表结果已经说出口——交付链自己走 pending → rendering → sending，并落进 三种可听语义之一。两条链通过 outbox（至少一次）衔接。

§9模块树与 SQLite 持久层

控制平面收敛在 agent/ 包内，纯标准库（sqlite3 内置），不 import 任何语音 客户端栈——这意味着路由、守卫、状态机、重入全部可以在无 GPU 环境下离线测试。语音前端与 控制平面的全部耦合都在 app.py 的工厂函数里以回调注入完成。

§12设计不变量

  1. 未说出口的不进历史——对话历史只收已上口 / 已确认的文本；路由快照与表达轮都从同一份历史取材。
  2. 跨层异步结果必须带代际校验——grace_ref_ts（宽限窗）、run_break 锚（双轨录音）、gen_sn / gen_serial（生成标志）、stop_event（话轮线程）都是"实例"而非"全局"：迟到的结果对不上号就作废，绝不过期生效。
  3. 确定性放 Runtime，概率性放模型——守卫、回执模板、状态机、lease 围栏、重播重入是代码；路由、表达、工具循环是 LLM；SQLite 是两者之间唯一的交接面。
  4. 语音前端是第一公民——Agent Runtime 只读注入：grace 阈值、话权结论、发声管线全部复用前端现有实现，不复制第二套"怎么说"。
  5. 门控旁路 fail-open——pvad / tse 不可用时放行音频：语音可用性优先于门控精度；tse 只上报不决策。
  6. 所有上话共用一条语音出口与三态语义——True=完整播出、False=播出后打断、None=从未起播；不存在第二套播放路径，也就不存在第二套打断语义。
  7. 空结果绝不谎报成功——慢脑空结果 → failed(outcome=empty)，宁可想个新办法，不把"没查到"说成"完成了"。
  8. 每一轮都必须有可听终态——回执、澄清、表达轮、无声兜底、ROUTER_FAIL_TEXT 五选一；无声轮是事故级别（listening 卡死家族的公共根因）。
  9. gen 标志必须释放——谁置位谁移交，话轮 worker 在 finally 里兜底释放（gen_serial 已变则自然 no-op）；漏放的后果是后台交付被永久拒绝。
