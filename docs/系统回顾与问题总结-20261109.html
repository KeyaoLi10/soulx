§1系统一句话与演进时间线

一个 0.6B 流式语义轮次预测模型（SoulX-Duplug）挂在 Qwen3.5-9B 快慢脑三实例 + VoxCPM2 流式 TTS 级联前端上，外加 pre-ASR 主说话人迟滞门控、五层话轮边界防御，以及 Agent Runtime 控制平面 （快脑语义路由 + 五道守卫 · 双路并行 · SQLite 持久化任务协议 · 三态交付 + 单一出口 + 重播重入）， 构成全双工中文语音对话系统。

十五天的演进可分四个阶段：

阶段 0 基础设施 10-26 ~ 10-29 · 服务能跑起来
  • FireRedTTS SYNCH_LOCK 死锁
  • WS 断线重连
  • 端口迁移 55556→8090
  • 内网 https 非安全上下文
  • TTS 换 VoxCPM2（流式）
  • Web UI 两次重设计
阶段 1 语音前端攻坚 10-30 ~ 11-05 · 听感与时序正确
  • 主说话人门控（PVAD→ECAPA 迟滞）
  • 音色漂移（锚定 + LoRA）
  • 幻影打断三连根修
  • 毛刺话轮五道门
  • 能量守卫 / 回声防御 / 打断截断
  • 双轨录音取证工具
阶段 2 快慢脑 Agent 10-30 ~ 11-05 · 任务委派可用
  • 快慢脑架构上线
  • 委派语域吞句
  • 霰弹枪工具调用（logits 级禁 token）
  • 快脑调工具三定律
  • 抢话宽限窗
阶段 3 Agent Runtime V2 11-06 ~ 11-09 · 协议化与实机化
  • 手册 P0–P5 实施
  • enforce 六事故
  • 路由提速三件套
  • 双路并行
  • 晚五~晚十二十二轮根修

§2当前系统设计与技术选择

2.1 分层架构

层组件职责
接入层浏览器（WebRTC AEC/NS/AGC）回声消除与降噪；16 kHz mono 上行 WS；24 kHz PCM 分块下行
门控层pvad 流门控 :8086（+ tse 影子 :8087，默认关）pre-ASR 迟滞门控：非主说话人音频压制为全零块，不进 ASR / 轮次判别
轮次层SoulX turn server :8000（GPU5）0.6B 状态机逐 chunk 判 idle/nonidle/speak；五道毛刺门；流式转写 + commit 后整句重识别
应用层Web app :8090会话管理、接收循环、话轮管线、宽限窗、能量守卫、回声防御、统一语音出口、双轨录音取证
Agent 层Agent Runtime（进程内 agent/）双路并行仲裁、路由 + 五道守卫、受控回执、SQLite 持久化、run 围栏调度、三态交付
模型层:6009 路由（GPU6，greedy 0）· :6007 闲聊/表达（GPU3，TEMP 0.9）· :6008 慢脑（GPU1）同一 Qwen3.5-9B 三实例各司其职
语音层VoxCPM2 :8085（GPU7）文本分句流式合成；自训 LoRA + 锚定音色 + 服务端正则化

2.2 关键技术选择及理由

  1. 级联而非端到端。moshi 类端到端全双工模型当时不可控、不可取证——级联每一级可独立观测 （双轨录音、turn.log STATE 行、route_log），事故可定位到 chunk 级。代价是延迟与跨层时序竞态，见 §3。
  2. 0.6B 语义轮次模型做话轮边界，而非纯 VAD / 纯静音阈值。语音前端全部时序参数 （turn_wait / grace / bargein）以它的状态机为第一公民。
  3. 双路并行（2026-11-06）。路由脑出计划要 3.5–4.3 s，用户等不起——闲聊路过 grace 门就开始口播 （应承 / 寒暄 / 按面板答），路由路后台做任务机器。仲裁规则保证永不双声道。这是全部"提速"与"吞句"根修的来源。
  4. SQLite 作为唯一交接面。请求 / 任务 / 事件 / 交付 / outbox 全部落库，operation_id 幂等、 run lease 围栏、事件只放已发生的事实。崩溃可恢复，离线可重放（全部离线回归测试就建在它上面）。
  5. 结果播报单一出口（交付泵）。闲聊路上下文永不注入结果原文（渐进式披露：只见状态摘要 + 用户实际听到部分），"再讲一遍"只能由泵兑现。代播记账（窄版 voiced-by-lane）只处理 "创建轮闲聊路已亲口说过 + 零工具自产内容"这一种。
  6. 守卫而非 prompt 补丁。路由层五道守卫（格式 / 接地 / 吞句 / 取消目标 / get_task 目标）+ 修复轮 ≤1。温度 0 下 few-shot 先验与硬规则的张力靠守卫在出口兜底——先验改不动，守卫清单随事故生长。
  7. 负结果也落库。声源分离（MossFormer2 拉不开 ECAPA 分数带）验证为负结果后仅影子集成上报 sep_cos，不参与决策；PVAD 背景视频失效调查记录了分数带完全重叠的定量事实。

2.3 设计不变量（从事故中提炼，详见流图 §13）

  • 语音前端第一公民——全部时序参数以其状态机为基准，上层适配它，不让它迁就上层。
  • 结构不合法绝不能执行——路由计划整批提交或整批丢弃，没有"部分执行"。
  • 幂等——operation_id 重放去重，同一操作重复提交不产生双重效果。
  • 引用封闭——quote 必须是本轮用户原话的子串，锚不到就不锚。
  • 传输故障 = 终态，没有修复资格。
  • 事件只放已发生的事实——计划是意图，不进事件库。
  • 一个会话一次只有一个声音——发言 owner 按 session 串行。
  • 开口前核验信封（SpeechEnvelope）——改口 / 取消 / 旧修订的结果不播。
  • speak_fn 三态（True / False / None）与语音前端逐条对齐。
  • 吸收轮也要释放 gen——任何早退路径走 finally。
  • 取消不是失败——被取代话轮静默退场，绝不说"任务执行失败"。
  • 面板不吊人——suppressed / interrupted / voiced_by_lane 都不渲染"结果待播报"式的永不兑现承诺； 闲聊路拿死承诺会无限复读。

§3主要问题与解决方案（按层归类）

3.1 服务可用性（阶段 0）

  • 几轮后整体沉默FireRedTTS SYNCH_LOCK 锁横跨 yield，全服务锁死
    →
    根修锁作用域；排查口诀"服务沉默先 curl :8081/health"
  • 几轮后不再转写浏览器 WS 掉线后前端无重连
    →
    前端重连 + 常驻重连按钮（后又修过一次缓存击穿）
  • 内网麦克风报错非安全上下文
    →
    放弃自签 https，改浏览器 flag 方案
  • TTS 延迟 / 音色FireRedTTS 非流式
    →
    换 VoxCPM2 流式分句合成（后续为此修了一整族问题，见 3.4）
思路：可用性问题先建可观测（健康检查、/logs.html、/sessions.html 时间线 + 双轨录音）， 再谈修复——后面所有时序类根修都依赖这套取证基建。

3.2 语音前端时序（阶段 1，密度最高）

  • 安静环境"幻听"（凭空转写出话）呼吸 / 轻笑进状态机
    →
    turn server 侧五道结构性毛刺门（预 latch 概率 / RMS 门 / 无文本降级武装 wait / 空 commit 守卫 / 种子裁剪）；文本旁路 latch 移除
  • 播放期幻影打断（自己打断自己）回声进转写 + 判别
    →
    三层回声防御（滑窗 / 假 turn 丢弃 / 自说自话过滤：回声物理窗口 + 形态两门）
  • 生成期幻影打断（首句被吞成"是。"）假 turn 被当成打断
    →
    生成器生命周期与假 turn 判定解耦
  • 抢话（用户刚停就抢答）complete 触发即开口
    →
    宽限窗（grace）+ wait 提交必先经 incomplete + complete 高能量挂起（RMS≥0.06）+ wait 计数 RMS 否决
  • 打断后音频尾巴没切干净run 戳在首写晚于 first_emit，epoch 比较是死代码
    →
    run 身份制：run_break(since) 记 first_emit + cut_pending_audio 铺五咽喉点
  • "你说 / 你是"类 partial 闪现partial 同音瞬态
    →
    前端前缀确认稳定性门
  • 打断交付"已听到部分"丢失结果 note 已进历史但音频被切
    →
    delivery_heard 回写 + 闲聊路渐进式披露（≤120 字）
思路：所有时序 bug 的修法收敛为一个模式——给每个异步参与者一个可验证的身份 / 时间戳 （run 身份、播放时钟锚定、线程标识防串门），把"猜时序"变成"对账"。取证靠双轨录音回放 （TTS 旁路 run 索引锚播放时钟，RTF≈0.36）与 turn.log STATE/TURN 常开行。

3.3 声学门控：谁在说话（阶段 1，两个负结果）

  • 旁人 / 背景视频也会触发对话浏览器同人 ECAPA 分 0.15–0.57 < 阈值 0.5，区分不了
    →
    默认直连不门控，代码保留
  • 背景视频话轮漏入分离带与主说话人分数带完全重叠，无阈值可切；参考漂移（混音轮污染 enroll）
    →
    pre-ASR 独立通道迟滞门控（用户语音 0% 误压 / 视频 95% 压制）；声源分离立项验证后主动止损，仅影子集成
  • MossFormer2 分离说话人内方差 > 说话人间差，拉不开 ECAPA 分数带
    →
    负结果记录在案，不参与决策
思路：门控问题先做分数带定量分析再谈阈值；分数带重叠就承认现有信号不够， 宁可负结果止损也不上误杀用户的门。

3.4 TTS 质量（阶段 1~2）

  • 跨段音色漂移无锚定参考
    →
    参考克隆锚定 + 自训 LoRA
  • 数数音色崩LoRA checkpoint 枚举不稳
    →
    A/B 定量协议定位到 step_0000400，回退 500；换 checkpoint 须 anchor 一致
  • 小数被切碎文本正则化缺陷
    →
    服务端正则化修复
  • TTS 念出 "assistant"标签泄漏进合成
    →
    文本清洗
思路：音色问题必须 A/B 定量（同 seed 同 anchor 对比），不接受"听着好像好点了"； 换权重 / 参数必须留回退路径。

3.5 Agent 语义层（阶段 2~3，当前主战场）

这是最重的一族，十二轮"晚 N"根修全部在这里。按问题模式分四类：

(a) 路由判错 — 该建任务的不建 / 不该建的建了

  • 委派语域吞句讲笑话 / 数数被推迟到任务
    →
    快脑 addon 硬规则 + auto_delegate 兜底；后又发现尾部注入 note 反而压低触发率（模型口头确认即停笔），移除
  • 讲笑话建成任务路由吃共享 LLM 历史最近 6 条（含 assistant 应承 + 结果 note 全文），任务形先验压过硬规则
    →
    路由 user 侧历史瘦身：只留 role=="user" 且非系统提示前缀
  • 错取消（"重新数到十"错杀 T2 毒化 T3）
    →
    取消目标接地守卫（label 二元组命中或纯取消话，否则修复 + 终态拒）
  • 错锚定（"你刚刚数到几了"被 get_task 锚到 interrupted 任务）
    →
    get_task 目标接地守卫 + interrupted 补全（本轮清账）

共性根因：温度 0 贪心解码下，few-shot 先验与硬规则的张力。共性修法：出口守卫（结构化、可测试），不做 prompt 场景补丁。

(b) 交付时序 — 结果什么时候说、谁说、说几遍

  • 湖人幻觉 + 循环播报闲聊路拿不到事实却被迫播结果
    →
    单一出口：结果播报收归交付泵，闲聊路只说桥接短语
  • 复读（"我去查一下"×4）路由延迟 > 用户开口间隔，请求永远 registered
    →
    长间隔落地 land_pending + 8s 续说合并窗口 + 在途路由有界等待 ≤5s
  • 重复交付崩溃循环交付行终态后重复 deliver 项再渲染
    →
    _DLV_ALREADY_HANDLED 直接收尾 + record_delivery 身份去重
  • 短应答掐死播报（"嗯，好的"杀掉 NBA 播报）
    →
    hold 语义：播报期间 held 话轮不 cut/interrupt/reset，真上口由 _speak 自己替换
  • 笑话挂"待播报" 1 分 54 秒创建轮闲聊路已讲过，任务零工具结果仍排队等泵
    →
    窄版 voiced-by-lane：创建轮已亲口说过 + 零工具自产 + 首 run → 泵不入队（判别器是零工具——查询类必带工具照走泵；数据源是 slow_brain 的 tool_call 事件，因为 tool_calls 表是无写入方的预留 schema）

共性根因：双路并行后"谁有资格说话"不再自明。共性修法：单一出口 + 开口前核验信封 + 面板不吊人。

(c) 生命周期泄漏 — 资源 / 请求 / 任务悬空

  • 纯应答吸收泄漏 gen 标志14.5s 无声事故
    →
    所有早退路径走 finally
  • 空流误报成功投递根本没发生却报 True
    →
    三态返回（True / False / None：没听过谈不上拒绝）
  • 取消竞态取消落在"结果正在播"窗口里，整段听完已取消内容
    →
    同态幂等 + 取消掐在途播音（stop_speaking_for_task 跨线程置 stop_event）
  • 查询蒸发路由结果被新话轮作废，查询从未发起
    →
    land_wait_prev + stale 复查 + user_stop 伴生断流

(d) 快脑工具行为

  • 霰弹枪工具调用（83s / 30 调用 + 幻觉结果作答）解码飘出对话标签
    →
    logits 级禁 <|im_start|> token 根修
  • 搜索慢
    →
    DDG 回落 + Tavily + 工具轮数上限 3

3.6 工程纪律（人的因素）

  • 重启 web 必须内联两个 env（丢了 AGENT_CONTROL_ENDPOINT 会静默回退 :6007 还能跑但不提速； 丢了 MODE 会被前端回推翻回 legacy）——已把模式钉死（env 恒优先 + settingsSyncedByAck 拦截）。
  • 测试脚本不得污染持久化设置（persist:true 才落盘）。
  • 仓库统一（内层仓 subtree 并入外层，单一仓库）。
  • 重启 turn server 必须内联 CUDA_VISIBLE_DEVICES=5（裸启落 GPU 0）。

§4方法论沉淀（怎么修出来的）

取证先行每轮事故 先纯取证（sqlite 事件库 + 双轨录音 + turn.log/web.log 锚点行 + headless 浏览器重放）， 向用户交付根因链并讨论修法后才动手。复盘文档全部落 docs/。
泛化优先长期约束 拒绝 task-specific few-shot 补丁，事故先找守卫 / 状态机 / 渲染收敛修法；产品取舍留用户。
离线回归先行修完即测 九套件 + 语音回放四件（selftalk / empty_stream / smoke / pvad_stream）+ 前端假 WS 重放； 事故修完先补回归再部署。AST 抽取真函数源码执行保证测试打的是真代码。
A/B 定量音色 / 温度 / checkpoint 同条件对比，不接受"听着好像好点了"；"数数音色崩""温度事实"都是 A/B 或查证纠正的。
保守方向失败判别信号不干净时 宁可放行也不误杀（空 run_id 判 False 走泵；门控分数带重叠就不上门控）。
承认负结果声源分离 / 背景视频 / 尾部注入 验证为有害 / 无效就下线，记录在案，不为沉没成本续命。

§5当前残留风险（已知未修）

  1. 交付泵单线程：speak_fn 占住期间，排队路径的 stop_speech 要等本轮播完 （跨线程 stop_speaking_for_task 已接，队列路径仍串行）。
  2. GPU6 / GPU3 是公共卡：邻居回驻则路由延迟回升（历史上发生过一次，挪卡解决）。
  3. 路由先验张力：温度 0 下 few-shot 先验与硬规则的张力仍靠守卫在出口兜底—— 守卫清单随事故生长，每类新错法都要再补一道（本次三修就是补了错锚定与代播记账两道）。
  4. 门控层默认直连：旁人语音与用户语音在浏览器 AEC 后不可区分，多人场景不可用。
  5. 工具调用延迟仍偶发：霰弹枪虽根修，慢脑单轮 gen≈max_tokens÷25 tok/s。

§6改进方向

6.1 当前可做（工程项）

  • 路由提速的下一步：3.5–4.3 s 仍是体验瓶颈。候选：快照渲染缓存与增量更新 （历史瘦身后 user 侧历史可预拼）、few-shot 再裁剪、或蒸馏 / 换更小的路由专用模型 （路由是分类问题，不需要 9B 的生成能力上限）。
  • 交付泵优先级队列：按话轮状态（用户在说 → 暂缓；静默期 → 立即）调度排队的 deliver 项， 消除残留风险 1。
  • 守卫覆盖率统计：route_log 已有全部修复 / 拒绝原因——做一张守卫触发率面板， 先验张力（残留风险 3）从"随事故生长"变成"有数据指导什么时候该上微调"。
  • GPU 专用化：把 :6009 / :6007 挪到独占卡（或向集群申请），消除邻居回驻的延迟回升。
  • 会话健康看板：把排查速查表（症状 → 先看什么）做成 /sessions.html 的自动诊断列 （requests registered 堆积、gen 卡 True、delivery 终态分布），实测时先看面板再 grep。

6.2 以后可进一步尝试（研究项）

  • 带参考的目标说话人提取（target-speaker extraction）：声源分离负结果的正确续集—— 不做无参考分离，用用户 enroll 声纹做引导，或从声学模型中间层取特征替代 ECAPA 分数。 做成可 A/B 的独立立项（当前影子集成 sep_cos 的管道可以直接复用）。
  • 端到端全双工模型对照：工作区的 eot / FDB 基建（moshiko / PersonaPlex、FDB v1.0 评测） 可以给 SoulX 的级联前端做对照打分——量化"级联 vs 端到端"在打断延迟 / 回声鲁棒性上的真实差距， 为下一代架构决策提供数据。
  • 路由器微调：当守卫触发率数据证明先验张力是主要误差源后，用 route_log 里 "守卫修复前后"的计划对做 SFT 数据（守卫已给出正确标签），把规则内化进路由模型。
  • 话轮模型与 Agent 协议的联合训练：SoulX-Duplug 目前只看声学 / 转写，不看任务状态； delivery hold 语义是外部补丁——长期可以让轮次预测吃任务面板状态（输入是结构化状态而非文本注入）。
  • 长记忆与个性化：SQLite 事件库已经把全部会话结构化，为跨会话记忆 （用户偏好 / 未完结任务的隔日追问）提供了现成底座。
  • 多人场景：依赖第一项（带参考的说话人提取）打通"谁在说话"，之后才是多说话人轮次仲裁。
