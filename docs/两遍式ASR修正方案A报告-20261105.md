# 两遍式 ASR 修正（方案A）报告（2026-11-05）

**会话**：cffc8a87（同日 ASR 三个问题的延续）
**背景**：用户提出"当前 ASR 经常不准"，并问：paraformer 是否流式？如果只在模型接管话权处，把整段语音交给一个离线 ASR（如 FireRedASR）重识别修正，结果能否更好？时延能否接受？

## 1. 事前测量（决策依据，37 个真实话轮）

- **paraformer 不是流式的**：现链路是"伪流式"——离线 paraformer-large（`asr_nat`）对 3.2s 滚动 `cascade_buffer` 反复整窗识别 + LCS 文本 diff 出增量。
- **live 文本错误来源**（为什么 commit 文本差）：3.2s 窗口截断；语音块拼接**无停顿**（buffer_for_asr 只装语音块，自然停顿全部丢失，而 paraformer 内部 VAD 恰恰依赖停顿）；合成 seed 头部；diff 摩擦。
- **整段重识别实测**（mic 侧车 PCM 切出 37 个话轮）：paraformer 78-260ms / FireRedASR-AED-L 79-410ms，**都可接受**；两者准确率互有胜负，而 turn server 已经加载着同一个 paraformer——**方案A（复用 paraformer，零新增基础设施/GPU）** 胜出。
- 典型案例：「你插到哪了？有点。」→「你查到哪了？兄弟。」；「我们。」→「嗯，行吧行吧。」
- 附带发现：FireRedASR 吃 **int16 幅度**波形（frc_services `load_audio` 不归一化），喂 [-1,1] 浮点会整体幻觉成流畅新闻——部署备忘。

## 2. 设计

commit 消息照旧先带 live 文本；turn server 紧接着用已加载的 paraformer 对**整段话轮音频**离线重识别，推送一条 `turn_final` 修正；web app 管线开头 hold 一个 ~500ms 窗等修正（超时/空文本回落 live 文本），修正文本替换后**全链路生效**：用户气泡 final、LLM 历史、自说自话检查、agent cancel。

关键约束的落法：

| 约束 | 落法 |
|---|---|
| TurnModel 跨会话共享、多处中途 reset() | 话轮音频累积放**每会话的 engine**（`turn_audio`），不碰模型缓冲 |
| ws 协议"一 chunk 一响应" | client `process()` 收包循环：吞掉 `turn_final` 暂存、继续 recv 到配对的 `turn_state` |
| 修正不能阻塞事件循环 | server 侧 daemon 线程跑 `correct_turn_text`；app 侧等待在 pipeline_worker（后台线程），**从不进 async loop** |
| modelscope pipeline 非线程安全 | `asr_lock` 串行化全部 recognize 调用（原 3 处 + 修正） |
| 修正与话轮配对 | server 端 `commit_seq` 戳进 commit 的 `turn_state`，`turn_final` 回带同 id；client 按 id 暂存/取用（留最近 8 条） |
| 空修正 | `text=""` 也推送——app 的等待窗立即解锁而不是烧满超时；app 侧空文本=保持 live |
| 话轮间静音不膨胀修正输入 | engine 累积从首个过 RMS 门（0.01）的块开始，1.6s 预卷环保住词头；尾部 35s 封顶 |

## 3. 实现（repo 仓 `d8ed707`）

- `service/model.py`：`asr_lock`；`_recognize()` 串行化包装（3 处调用点替换）；`correct_turn_text(audio)`（<0.3s 或异常返回 ""）。
- `service/engine.py`：`_accumulate_turn_audio` / `_take_turn_audio`；commit 时结果附 `corr_audio`。
- `service/session.py`：`commit_seq`。
- `server.py`：`json.dumps` 前弹出 `corr_audio`；`_correct_and_push` daemon 线程（turn_state 发出后才启动，保证本 chunk 的响应先到）；turn.log 新增 `FINAL session <8> id=N lat=X.XXs changed=0/1 text=...` 行。
- `dialogue_system/clients/vad_client.py`：`_send_and_recv` 收包循环、`_stash_turn_final`、`wait_turn_final(commit_id, timeout)`。
- `dialogue_system/app.py`：pipeline_worker 步骤 0——`asr_correct` 开（默认）时 hold `asr_correct_wait_ms`（默认 500ms）等修正；web.log `ASR corrected in X.XXs (path turn): 修正 (live: 原文)`；sessions 页解析并入 turn 事件。
- `settings.py` + 前端：`asr_correct` 开关 + `asr_correct_wait_ms` 滑条（0-2000ms），frc 模式灰化；sessions 页 settings chips 加 `asrfix`。

## 5. 已知边界

- **修正延迟串行代价**：`asr_lock` 下修正与主循环识别互斥，最坏情况下一个 chunk 的 feed_audio 被推迟一次识别时长（~0.1-0.4s，turn.log 的 SLOW feed_audio 会显形）。实测未见。
- 每话轮固定多等修正耗时（即便文本没变，典型 0.1-0.3s）——这是准确率换的，UI 可关（`asr_correct`）或调窗（`asr_correct_wait_ms`）。
- 中途被 reset() 掐掉的话轮（far-field/backchannel 守卫）音频不清理，会带进下一次修正的输入尾部——RMS 起始门 + paraformer 内部 VAD 兜底，极端情形修正退化为 live（可接受）。
- 修正只改文本，不改话轮边界判定（EOT 仍用 live 链路）——边界错误不在本方案范围。
